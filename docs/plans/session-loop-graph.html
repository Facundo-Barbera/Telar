1 · Today: nine entry points, four queues, two owners

Every box that authors a turn trigger is an owner. The core problem is on the left: the client authors machinery (wakes, watches, kickoff) and holds three of the four queues — so machinery only runs while a view is mounted, and each surface has its own send contract.

3 · The canonical loop (proposal)

Claude Code's own shape: one session loop, one ordered inbox. Every stimulus — user message, wake, watch, kickoff — is a typed item entering the same durable mailbox; one server-owned drainer claims at turn boundaries; clients are pure renderers + enqueuers. The two doors into the model stay exactly as they are (live process · appendix + evidence ack).

4 · What an agent can do today (everything the loop must carry)

Generation & SDK-native

  • text / thinking / tool calls, streamed
  • background Bash tasks (roster; Claude only)
  • subagents → dock conversations
  • auto-continuation on roster-empty (wake-hold, #85)
  • compaction — auto & manual, persisted dividers
  • permission asks: live card · parked card between turns · detached deny

MCP surfaces

  • ultra: launch / status / inspect / stop — detached runs, wake mailbox on terminal
  • loom: start / answer / steer / watch / bundle … — verification runs, watch → injection
  • workspace: items + lanes CRUD
  • browser: shared tabs — navigate, snapshot, click, type…

Lifecycle acts on the session

  • Stop = interrupt-first, keep-what-arrived (F2)
  • queued message edit / cancel / reclaim (F0–F1)
  • rollback — designed, not shipped (F3)
  • settle stays user-driven — no external trigger shelves a session

Provider asymmetries

  • Codex: no roster, no background window, per-turn child process
  • appendix reaches Codex as instructions (same string, same ack evidence)
  • ultra authoring is Claude-gated; wake delivery is not

5 · To discuss

Q1 — Server-owned machinery. Move wake/watch trigger authorship from useSessionInjections into the engine: ultra terminals and watch firings enqueue mailbox items server-side (idempotency key runId+terminalAt / watchId+state). Kills D8 (no mounted view needed), makes D4-class loops structurally impossible (one item per terminal, ever), and the client injection queue disappears. Cost: the engine needs a small subscription/scan loop — which Q2 wants anyway.
Q2 — Heartbeat. A lazy engine timer (e.g. 30s, only while any queue non-empty or any run non-terminal) closes D5 starvation and gives Q1 its scan cadence. Cheap, bounded, no per-session cost when idle.
Q3 — One send contract. Do all surfaces enqueue-always (dock's shape), with the engine claiming instantly when idle? Uniform ordering and retry; costs one queue write of latency on the idle fast path (measurable, likely ~ms). Alternatively keep the direct-POST fast path but make the dock use it too — either way, one contract.
Q4 — Steering (Claude Code parity). Today a message typed mid-turn waits for the next turn. The runtime already holds a streaming input channel — F2's infrastructure allows pushing a queued user message into the live turn as a correction. Ship after F2's interrupt lands, as an opt-in per message ("Send now")?
Q5 — Machinery turn UX. Hidden wake turns render nothing until output arrives (#71's remaining "responding" shimmer). If machinery becomes mailbox items (Q1), the strip can honestly show "waking for ultra sweep…" as a queue row — the UI stops pretending nothing is happening.
