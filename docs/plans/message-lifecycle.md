# Message Lifecycle — cancel, reclaim, rollback (design)

Produced 2026-08-07 from a four-source understanding pass (SDK 0.3.224 typings, Claude Code/Codex interaction grammar, t3code's rollbackThread + checkpointing, Telar's own anchors audit). Governs F1-F4 below; composes with the baseline feel contract.


## FEATURES

MESSAGE LIFECYCLE — one intent ("that message shouldn't have gone / shouldn't have gone like that") at four distances from the moment of sending. The family is layered so each layer ships alone and none of them invents vocabulary the feel contract bans (no "checkpoint", "rewind", "fork", "branch", "revert"; the only verbs are Edit, Send, Stop, Remove).

F0 — THE FLOOR (already shipped, restated as the contract the rest must compose with). Pending strip above the composer: your messages, in order, waiting to send, editable in place, no lifecycle badges by construction (`pendingView`, /Users/bixku/Projects/Telar/apps/web/lib/message-queue.ts:172-207). Claimed/running items have NO strip line — the transcript owns them. Stop holds everything un-sent client-side; the next send releases it.

F1 — CANCEL-TO-EDIT (a message that has not been claimed).
Behavior: the message leaves the strip whole — text AND attachments — and lands in the composer with the caret at the end. Nothing is left behind, nothing is duplicated.
Triggers: (a) ArrowUp on an EMPTY composer, repeatable — each press walks one line further up the strip (newest → oldest), ArrowDown walks back down and the last ArrowDown restores whatever draft was displaced; (b) the pencil on a strip line (in-place edit, unchanged); (c) the ✕ (discard, unchanged).
Two defects in today's path this feature closes: `recallPendingIntoComposer` (session-view.tsx:3166-3187) recalls only `pendingLines.at(-1)` and copies only `line.item.text` — a queued message with attachments comes back silently lighter, which is exactly the "never hand back less than you were given" rule `writeQueue` already honors for storage.
The lost-race case is part of the feature, not an error: core admits no edit/cancel once an item is `claimed` (packages/core/src/session-queue.ts:353-392), and Telar's engine claims the instant `isSessionRunLive` goes false. When the pull-back loses that race the answer is not an error banner — it is the handoff to F2: one line at the strip, "That one already went.", with Stop right there.

F2 — STOP-AND-RECLAIM (the message that is in flight).
Behavior, three things at once: (1) the turn stops — the running tool call is cancelled and the session's process, its warm context and its background agents SURVIVE (today's Stop kills all of it); (2) everything that arrived is kept and marked — streamed text flushed, outputless tool calls flagged `interrupted`, the exchange persisted, one non-attention marker under it: "Stopped — kept what arrived."; (3) your words come back editable — into the composer if it is empty, otherwise to the HEAD of the pending strip (never destroy typing), with the strip held so nothing auto-fires.
Triggers: Esc-Esc while busy (existing arming, ESC_ARM_WINDOW_MS, session-view.tsx:2622-2680) or the Stop button. Identical act, one code path — the existing "ONE STOP, TWO TRIGGERS" rule holds.
THE SHARPEST CALL IN THE FAMILY: **Stop does not rewind the model.** The stopped turn may already have edited files, run commands, spawned agents. Truncating its conversation while its side effects stand produces an agent with amnesia about work it really did — the worst possible state, and one no undo can repair. So Stop keeps the exchange in the model's memory too; the user's re-sent, edited message reads as a correction (which is what Claude Code's Esc does: "Claude keeps the work done so far"). If the user wants the model to forget it as well, that is F3, and it is offered inline one line below, exactly where they are looking.

F3 — ROLLBACK (edit any past user message and send from there).
Behavior: the chosen message's text and attachments load into the composer; everything from that message down renders dimmed under a single rule with one label — "Replaced when you send" — plus, when it is true, one plain clause: "3 agents from these messages will be stopped." and "Your files stay as they are." NOTHING is destroyed at click time. Sending truncates the transcript for real, rewinds the provider's own memory to that point, and runs the new turn. Escape, or "Keep it" on the label, cancels and restores the transcript with nothing lost.
Triggers: (a) the pencil in the gutter of any past USER bubble (same affordance language as the strip's pencil — the act lives on the thing it acts on, no picker, no menu); (b) Esc-Esc on an EMPTY composer while IDLE = the previous user message (Codex's grammar; extends today's arming, which only listens while `busy`).
Sub-case, shipped first because it is the only case where the SDK's guard is exactly valid: ROLLBACK OF ONE — "Remove this exchange", offered inline under a turn you just stopped.
Explicit non-target: turn 0. The first user message has no pencil. Rolling back "to before the beginning" would require a new SDK session id, and `Chat.id` IS the SDK session id — it keys the runtime map, sessions/<id>/ feed dir, queue.json, the usage ledger and every permalink. The honest alternative offered instead is "New session with this text" (a fresh composer, prefilled). For the same reason Telar's rollback TRUNCATES IN PLACE and never sets `forkSession: true`: minting a new id renames the session out from under everything.

F4 — FILE STATE: what is in scope now.
In scope: telling the truth and nothing more. Rollback never touches files, and the dim label says so in one clause. Optionally (one cheap `git rev-parse HEAD` per turn, degrades to absent) a per-turn `anchor.git = { head, dirty }` stamp, which costs a line and unlocks the deferred work later.
Deferred, with its shape recorded so it is not re-derived: a git-ref checkpoint store on t3code's proven shape — `refs/telar/checkpoints/<b64url(sessionId)>/turn/<N>`, captured with an isolated `GIT_INDEX_FILE` + write-tree/commit-tree/update-ref (no HEAD move, no branch move), restored with `git restore --source <oid> --worktree --staged -- .` + `git clean -fd`. It must not be built before one question is answered: Telar runs many sessions against ONE project worktree (git ops in /Users/bixku/Projects/Telar/apps/web/lib/server/git-workspace.ts all take a plain `root`, there is no per-session worktree), so a restore is cross-session destructive in a way it never is in a one-terminal CLI.
NOT RECOMMENDED, firmly: wiring `enableFileCheckpointing` + `Query.rewindFiles()` (sdk.d.ts:1484, 2539). Four reasons, each fatal on its own for Telar specifically: it does not capture background-subagent edits — and Telar's product IS background subagents; it does not capture Bash-driven changes (rm/mv/cp) — and Telar's agents live in Bash; it is a method on a LIVE `Query` object that Telar reaps after 30 minutes idle and recreates via `resume` (session-runtime.ts:95, IDLE_REAP_MS), so the undo history is exactly as durable as a process; and it is Claude-only, where git covers every writer including Codex. Git is the right substrate for this app; the SDK's file checkpointing is the wrong one.

## MECHANICS

F1 — CANCEL-TO-EDIT. No provider ever saw the message; there are no SDK calls at all. Server surface is unchanged: PATCH/DELETE /api/chat/[sessionId]/queue/[itemId] → `editQueuedSessionTurn` / `cancelQueuedSessionTurn` (queued-only, optimistic `expectedRevision`). Runtime, feed and window are untouched. Codex: identical, because the queue is Telar's own and provider-blind.
Failure modes: (i) revision conflict or state≠queued → the item was claimed between render and click; do NOT surface a queue error — re-classify to the F2 handoff line and offer Stop. (ii) attachment bytes archived away since queueing → recall the text and keep the chips as tombstones with one sentence, never a silently lighter message.

F2 — STOP-AND-RECLAIM.
SDK: `query.interrupt()` (sdk.d.ts:2346), streaming-input only, which Telar already is. Note what is NOT reachable in the pinned 0.3.224: the typed `interrupt()` takes no arguments, so `cancel_queued: true` and `cancel_async_message` (sdk.d.ts:3618, 3142) exist only on the raw control wire and are not part of the public `Query` surface (verified by reading every method on the interface). Telar does not need them — its queue is queue.json, and it pushes at most one user message per turn — but it must READ the receipt: a non-empty `still_queued` means the CLI has an internally-enqueued continuation (cron, auto-resume) that would start a turn nobody asked for right after a Stop, so a non-empty receipt ESCALATES to `closeNow`. Feature-detect via `query.initializationResult()` capabilities (`interrupt_receipt_v1`); an older CLI resolves `undefined` and is treated as "unknown, do not escalate".
Runtime lifecycle — and this is why F2 is small: an interrupt makes the CLI end the turn with a `result` (subtype `error_during_execution`, `terminal_reason: 'aborted_streaming' | 'aborted_tools'`, sdk.d.ts:4416-4436). The pump already ends a turn's feed at `result` (session-runtime.ts:216-222), so the POST's for-await unwinds NORMALLY and the existing teardown does the whole "kept and marked" half for free: `flushStreamingText`, `markInterruptedTools`, `send("interrupted", {})`, `rationToolDetail`, `appendTurn` (route.ts:2478-2500). A bonus that is worth naming: today's Stop aborts, so `lastResult` is null and spend falls back to the experimental usage probe; an interrupt DELIVERS a result, so cost/usage accounting on a stopped turn gets more accurate, not less.
New server surface: `interruptSessionRuntime(key)` in /Users/bixku/Projects/Telar/apps/web/lib/server/session-runtime.ts, and /Users/bixku/Projects/Telar/apps/web/app/api/chat/stop/route.ts becomes interrupt-first. Critical wiring detail: today `abort.signal` is bound to `runtime.closeNow` (route.ts:2121) and `stopChatRun` trips it. The interrupt path must NOT trip that controller — it fires the control request and arms a watchdog; if no `result` lands within ~5s, it escalates to `stopChatRun(key)` + `closeSessionRuntime(key)`, i.e. exactly today's behavior. "Stop means stop" stays literally true; it just tries the gentle door first. Permission cards are unaffected: the turn's `finally` still runs, `windowContinues` still decides whether parked cards stay answerable.
Feed/window: an interrupt ends the turn at `result` like any other turn, so the window sink installs and the background tail continues normally — background agents that outlive the stopped turn keep rendering, which is the ENTIRE point of preferring interrupt over closeNow.
Codex degradation: none needed, and nothing to preserve. Telar's Codex path spawns a fresh app-server child per turn (`runCodexTurn` in /Users/bixku/Projects/Telar/apps/web/lib/codex-app-server.ts; `onAbort = () => client.kill()`, and the `finally` kills it anyway), so there is no warm process an interrupt would save. Codex Stop stays "kill the child"; the reclaim half (text back, partial output marked, marker line) is pure Telar bookkeeping and behaves identically on both providers.
Failure modes: `interrupt()` rejects or hangs → watchdog → closeNow (today's behavior). Receipt reports survivors → closeNow. The interrupted result arrives AFTER the receipt on a clean interrupt but may precede it on a crash (the SDK documents this ordering) — so never gate teardown on the receipt; treat it as advisory. Unverified and probe-gated: whether a runtime is reusable for the NEXT turn after an interrupt. If it is not, close it gracefully after the interrupted result and let the next POST recreate with `resume` — one process spawn, zero correctness loss.

F3 — ROLLBACK.
SDK (Claude): `resume: <sessionId>` plus `resumeSessionAt: <uuid>` (sdk.d.ts:1817 — "only resume messages up to and including the message with this UUID", accepts ANY chain-entry uuid) and, in exactly one case, `resumeDropsTurn: <promptUuid>` (sdk.d.ts:1868). Two things about `resumeDropsTurn` decide the design: it is PRINT/HEADLESS-LANE ONLY — which is precisely the lane the Agent SDK's `query()` boots, so Telar's truncation IS honored — and it declares ONE dropped turn. Therefore: pass it only when the rollback discards exactly the last turn (the F3-of-one case); omit it for any multi-turn rollback, which keeps the unguarded truncation the option's own docs describe. Fork at the KEPT turn's LAST chain entry, per the option's general rule — never at "the last assistant uuid" reflexively.
Runtime lifecycle — the trap Source 3 flagged, closed by two independent means: `acquireSessionRuntime` reuses a warm runtime whenever the fingerprint matches and no turn is attached (session-runtime.ts:305-316), and `resume`/`resumeSessionAt` are only ever read inside `create()` (route.ts:1884-1898). So a rollback that only wrote a new fork target would be silently ignored by the already-open CLI, which has the full untruncated history loaded. Rollback therefore ALWAYS calls `closeSessionRuntime(sessionId)` (`closeNow` — immediate abort, background tasks included), and the fork target is ALSO added to `runtimeFingerprint` (route.ts:1860-1883) as belt-and-braces. `closeNow` is the correct violence here for a second, independent reason: agents spawned by turns that no longer exist must not keep running and reporting into a history that no longer contains what spawned them. Conveniently, `closeNow` nulls `windowSink` and clears the settle timer before aborting (session-runtime.ts:407-419), so a window's `onSettled` cannot fire a late `appendTurn` into a transcript we are truncating.
Order of operations in `applyRollback(sessionId, toTurn, expectedTurns)`: (1) refuse with 409 if `isSessionRunLive(sessionId)` (/Users/bixku/Projects/Telar/apps/web/lib/chat-runs.ts:88) — the client's composite "Stop and edit" does stop → await stopped result → rollback, so the user still experiences one act; (2) `closeSessionRuntime(sessionId)`; (3) `settleSpawnStatuses(sessionId)` with NO ids — the existing repair sweep (store.ts:530-547) — so spawn parts in KEPT turns that are still ack-only get marked "stopped" instead of shimmering "running" forever over a session whose process we just killed; (4) truncate the store under an optimistic check (`chat.turns === expectedTurns`, else refuse with "Something landed while you were deciding — try again."); (5) arm the fork; (6) announce on the feed.
Feed/window interaction: `live.ndjson` and `feed.ndjson` both truncate at window start and hold only the current window (session-log.ts:9-11, 108-111), so there is nothing historical to trim — but OTHER subscribers (a second tab, a dock bubble) must learn the transcript changed. Use the existing primitives: `startSessionFeedWindow(sessionId, rollbackId, "", /* hidden */ true)` to bump `win` and write the header, then `appendFeedEvent("rolled_back", { turns: toTurn, messages: newLength })` and `appendFeedEvent("closed", {})`. Every tailing client's stale `{win,seq}` re-bases (readFeedEvents replays the whole window when `after.win !== parsed.win`, session-log.ts:238), sees `rolled_back`, truncates its local transcript to `messages`, and the `closed` line ends the tail. No new transport, no new file, no rotation policy.
The refusal ladder (deterministic, per the SDK's own instruction never to retry a refused fork): the CLI answers a bad `resumeDropsTurn` with a result whose message starts `Resume rejected by --resume-drops-turn:`. Detect that prefix in the route; then (a) drop `resumeDropsTurn`, close the runtime, re-run the same turn ONCE — this is not a retry of the refused request, it is the documented unguarded truncation, and it is invisible because nothing has been persisted yet; (b) if that also errors, clear `pendingFork`, keep the truncated transcript, and append ONE marker part (`{type:"marker", attention:true}`, the primitive already exists) reading "The agent may still remember the messages you removed." Being honest in one line beats being silently wrong.
Codex support — and here Codex is EASIER than Claude, which is worth saying out loud: the app-server has a native ledger truncation RPC, `thread/rollback { threadId, numTurns }`, which t3code already drives (CodexSessionRuntime.ts:1840-1852) and which truncates the provider's own transcript for real. Telar has the exact precedent for adding it without touching the turn path: `runCodexCompact` opens its own short-lived client, `thread/resume`s, and issues one top-level request (codex-app-server.ts:1146-1153). Add `runCodexRollback({ threadId, numTurns, env })` in the same shape. `numTurns = chat.turns - toTurn`, and it is exact because Codex has no background windows (the child dies per turn), so Telar's anchor array is 1:1 with Codex turns. Degradation: a JSON-RPC method-not-found from an older app-server → the same honest marker as the Claude ladder's floor. Mixed-provider ranges are refused with one sentence — a range that spans both providers cannot be truncated by one mechanism.
Remaining failure modes, stated because they will happen: rollback while queue.json holds items — the queued words were written for a conversation that is about to change, so they must not auto-fire; reuse the existing client hold (`heldAfterStop` / `turnInterruptedRef`, session-view.tsx:3051-3068), which already pulls engine-queued items back to local drafts so they can be re-ordered (core has no reorder primitive; the pull-back is what makes head-insertion possible). Rollback of a turn whose background agents are STILL live — covered by step (2)+(3) above, and the dim label says how many will be stopped before the user commits. Spend — untouched, always: `usage.ndjson` is append-only and every spend readout is a projection over it (AD-18, store.ts:299-340); money spent on discarded turns was really spent and stays. Compaction anchors — see persistence.

## PERSISTENCE

Everything below is in /Users/bixku/Projects/Telar/apps/web/lib/store.ts unless stated. The governing constraint: `ChatMessage` is `{ role, parts }` with no id (store.ts:145-148), the SDK message uuid is captured at projection time but discarded at end-of-turn (`ClaudeTurnState.partOrigin`, /Users/bixku/Projects/Telar/apps/web/server/providers/claude/project-message.ts:70-73, 190 — explicitly "scratch bookkeeping", never a parameter of `appendTurn`), and `appendTurn`'s signature (store.ts:626-666) has nowhere to put one. So the mapping from "this point in chats.json" to "the uuid the SDK needs" does not exist and must be created.

1. NEW TYPE — a per-turn anchor, anchored by message COUNT, deliberately the same idiom `CompactionRecord.afterMessages` already uses ("an index, not a message id: the store's messages have no ids of their own", /Users/bixku/Projects/Telar/apps/web/lib/compaction.ts:50-52):

export type TurnAnchor = {
  startMessage: number;   // chat.messages.length BEFORE this turn appended
  endMessage: number;     // and after — so a hidden turn (1 message) is not assumed to be a pair
  provider: "claude" | "codex";
  at: number;
  hidden?: boolean;       // mirrors hideUserMessage: kickoffs and window-settle follow-ups
  prompt?: string;        // uuid stamped on the pushed SDKUserMessage — the resumeDropsTurn value
  tail?: string;          // last main-thread chain-entry uuid observed for this turn — the resumeSessionAt value
  contextTokens?: number; // so a rollback restores an honest CTX instead of the newest turn's
  contextUsage?: ContextUsageSnapshot;
  git?: { head: string; dirty: boolean }; // optional, F4-in-scope, degrades to absent
};

2. `Chat` gains two optional fields (both absent on every existing chat, which reads as "not rollback-addressable" — legacy chats simply have no pencil, which is the correct false-promise-free degradation):
   - `turnAnchors?: TurnAnchor[]` — parallel to turns, index IS the turn number.
   - `pendingFork?: { resumeSessionAt?: string; resumeDropsTurn?: string; armedAt: number; degraded?: "unguarded" | "plain" }` — one-shot, spread into query options by `create()` and cleared when that turn's result lands.

3. `appendTurn` gains `provider` and `anchor?: { prompt?: string; tail?: string; git?: {...} }`, and computes/pushes the TurnAnchor itself from `chat.messages.length` before and after the push — the caller cannot get the arithmetic wrong, and the hidden-turn (one message) case is handled in one place. It also copies the `contextTokens`/`contextUsage` it already receives onto the anchor.

4. `ChatSummary` becomes `Omit<Chat, "messages" | "turnAnchors"> & { preview }`, and `listChats`' map drops `turnAnchors` alongside `messages` (store.ts:291-295). Anchors are per-turn objects; they have no business in every sidebar/dashboard payload.

5. NEW MUTATORS (same read-modify-atomic-rename discipline as every existing writer, store.ts:245-251):
   - `rollbackChat(id, { toTurn, expectedTurns }): { ok: true; messages: number } | { ok: false; reason }` — refuses unless `chat.turns === expectedTurns` (optimistic concurrency, the same shape core's queue uses); then `messages.length = anchors[toTurn].startMessage`; `turnAnchors.length = toTurn`; `turns = toTurn`; `compactions = compactions.filter(c => c.afterMessages <= newLength)` — which is what preserves the invariant compaction.ts calls "impossible today" (a record anchored past the transcript end, compaction.ts:228-231) and which a naive truncation would break; restores `contextTokens`/`contextUsage` from `anchors[toTurn-1]` (or deletes both, so the wheel reads "unknown" rather than a lie); `delete settledAt; delete snoozedUntil` (a rollback is a human acting in the session — the same un-shelving rule appendTurn applies, and no external trigger is involved, so "settle stays user-driven" holds); `updatedAt = now`. It does NOT touch `costUsd` and does NOT write usage.ndjson.
   - `armPendingFork(id, fork)` / `clearPendingFork(id)`.

6. WHERE THE UUIDS COME FROM.
   - `prompt`: Telar mints it. `SDKUserMessage.uuid?: UUID` is part of the input shape (sdk.d.ts:4748-4785), so the route stamps `uuid: crypto.randomUUID()` on the message it pushes (route.ts:2264-2268) and hands it to `appendTurn`. Probe-gated (step 0): if the CLI does not adopt a client-supplied uuid as the chain-entry uuid, `prompt` is simply absent and every rollback runs unguarded — a degradation, not a breakage, since `resumeDropsTurn` is optional by design.
   - `tail`: one new field on `ClaudeTurnState` (`lastChainUuid`), advanced by the projector on every MAIN-THREAD (`parent_tool_use_id == null`) `assistant` message and on every main-thread `user` tool_result message — never on `result` (the fork rule wants the last CHAIN entry, and a result's status as one is unverified). Deliberately not modelled on t3code's `lastAssistantUuid`, which is advanced by subagent snapshots too (ClaudeAdapter.ts:2850) and is never rewound, which is precisely why t3code's recomputed cursor points at the wrong place after a rollback. The window sink's detached projection advances it as well, so the background window's own follow-up `appendTurn` carries the true tail and a later rollback does not silently discard the background agents' work from the model's context.
   - Codex anchors need no uuids at all: the array INDEX is the anchor, because `thread/rollback` takes `numTurns`. `provider` on the anchor is what routes the plan.

7. WHAT DELIBERATELY DOES NOT CHANGE: usage.ndjson (append-only, projected — AD-18); `live.ndjson` / `feed.ndjson` (truncate per window, hold only the current one, so there is no historical feed state to rewind — session-log.ts:9-11, 108-111); the in-memory feed allocator (recovers from the file's last line and just continues its window count); queue.json (rollback holds it client-side, it does not rewrite it); and `Chat.id`, which stays the SDK session id forever.

8. WIRE POLICY: the client NEVER sees a uuid. /Users/bixku/Projects/Telar/apps/web/app/projects/[name]/sessions/[id]/page.tsx and /Users/bixku/Projects/Telar/apps/web/app/api/chats/[id]/route.ts project `turnAnchors` down to `{ turn, startMessage, hidden, at }` before it reaches `InitialChat`. Rollback is addressed over the wire by turn index + `expectedTurns`; SDK identity stays server-side.

## UI

The grammar in one sentence: every act lives on the thing it acts on, nothing is destroyed before you send, and no surface ever names a mechanism.

WORDS ALLOWED: Edit, Send, Stop, Remove this exchange, Keep it, "waiting", "Held — sends with your next message", "Stopped — kept what arrived.", "Replaced when you send". WORDS BANNED: checkpoint, rewind, fork, branch, revert, truncate, resume, cursor, anchor, and every lifecycle state name (`pendingView` already makes the last one structurally impossible).

WHERE THE AFFORDANCES LIVE.
- Strip line (not yet sent): pencil = edit in place; ✕ = discard; click the text = edit. Unchanged.
- Composer: ArrowUp on empty = pull the newest strip line in whole; press again to walk older; ArrowDown walks back and the last one restores the displaced draft. This is a pure index over `pendingLines`, so it belongs in message-queue.ts as `recallTarget(lines, cursor, dir)` with its own test, not as component state arithmetic.
- Past USER bubble (sent, answered): a pencil in the gutter, appearing on hover/focus of that bubble only — the same affordance language as the strip's pencil, which is what makes rollback read as "editing a message" rather than as time travel. Absent on the first user message, and absent on every chat with no anchors (a legacy transcript shows no promise it cannot keep — the same rule that removed the `title="Click to edit"` tooltip from non-editable strip lines).
- Under a turn you just stopped: one inline text button, "Remove this exchange".

KEYBOARD PATHS (no new keys; the Esc arming already exists and simply gains an idle branch).
- Esc-Esc while BUSY → Stop (F2). First press arms and relabels the send control to ESC, exactly as today.
- Esc-Esc while IDLE and the composer is EMPTY → stage a rollback of the previous user message (F3). Esc-Esc while idle with TEXT in the composer keeps its ordinary meaning (clear the field) — the same disambiguation Claude Code makes.
- Esc while a rollback is staged → cancel the staging, restore the transcript, leave the composer text alone.
- Enter → Send, always. There is no second send verb anywhere in this family.

WHAT RENDERS DURING.
- F2, at the moment of Stop: the working indicator ends; the assistant's partial reply STAYS with whatever arrived; tool calls with no result render as interrupted (existing `interrupted` part flag + the `interrupted` SSE event, which the client already applies locally); one non-attention marker under the exchange reads "Stopped — kept what arrived."; the user bubble gets a subdued trailing note, "returned to composer", so the duplicate text about to appear is legible rather than spooky; the composer holds the reclaimed text with the caret at the end, or — if the user had already typed something — the reclaimed message appears as the FIRST line of the pending strip and the strip is held. Background agents that survived keep rendering into the background tail, which is the visible proof that Stop stopped the turn and not the product.
- F3, while staged: the composer holds the message (with its attachment chips); from that message down the transcript renders dimmed under one rule with a single label line: "Replaced when you send" + "Keep it", plus at most two plain clauses when they are true — "3 agents from these messages will be stopped." and "Your files stay as they are." The pending strip shows its existing "Held — sends with your next message" header. No overlay, no dialog, no picker, no confirm step: the transcript itself is the preview, and it is reversible until Enter.

WHAT RENDERS AFTER.
- F3, on send: the dimmed range disappears, the edited message appears as an ordinary user bubble at its place, streaming starts under it. No divider, no "rolled back" banner, no summary card — the conversation simply is what it now is. A second surface (dock bubble, other tab) reaches the same state through the feed's one-line `rolled_back` window and re-renders the same way.
- If the provider refused to forget (both rungs of the ladder failed): one amber marker at the truncation point — "The agent may still remember the messages you removed." That is the only place this family is ever allowed to be wordy, and it earns it by being the one case where the screen and the model disagree.
- Costs and meters: CTX re-reads from the kept turn's anchor; spend does not move, ever. If a user asks why, the answer belongs in docs, not in a tooltip that apologizes on every rollback.

THE HANDOFF THAT MAKES THE FAMILY FEEL LIKE ONE THING: a pull-back that loses the race (F1) offers Stop (F2) on the same line; a Stop (F2) offers "Remove this exchange" (F3) on the line below; a rollback (F3) reuses the strip's hold and the strip's pencil. The user never learns three features — they learn one gesture that keeps working as the message gets further away.

## MIGRATION
