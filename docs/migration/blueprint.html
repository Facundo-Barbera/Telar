Anatomía de un dominio siempre la misma forma

Engine: apps/engine/src/domains/sessions/

sessions/ ├─ index.ts API pública del dominio (lo único importable) ├─ store.ts estado + persistencia (ex-EngineStore) ├─ routes.ts HTTP /v2/sessions/* con zod ├─ tools.ts herramientas MCP que ven los agentes ├─ *.ts lógica pura (create.ts, settle.ts…) └─ *.test.ts junto al archivo que prueba

Web: apps/web/src/features/sessions/

sessions/ ├─ index.ts lo que otras features pueden usar ├─ components/ SessionRow, TitleMenu… ├─ hooks/ useSessionSync, useSettling… ├─ api.ts llamadas al engine (vía EngineClient) ├─ model.ts lógica pura, sin React └─ *.test.ts(x)

Contrato: packages/engine-client/src/sessions/

sessions/ ├─ schema.ts tipos zod de request/response └─ client.ts métodos del EngineClient

iOS: apps/ios/TelarMobile/Features/Sessions/

Sessions/ ├─ SessionsStore.swift ├─ SessionView.swift └─ … misma palabra, mismo lugar

Las reglas cada una verificada por CI, no por buena voluntad

1
Todo código vive en un dominio o en platform/uiNo hay archivos sueltos en src/. Carpetas permitidas en la raíz de cada app: una lista fija.check:structure
2
Un dominio solo se importa por su index.tsNada de ../otro-dominio/store. platform y ui nunca importan dominios.lint de fronteras
3
Archivos ≤ 800 líneas, funciones ≤ 150Si tocas uno más grande, extraes lo que cambiaste. Meta: ≤ 500.oxlint + eslint, error
4
Comentarios: por defecto ningunoMáximo 3 líneas y solo invariantes locales. Lo que cruza dominios va a docs/internals/.ratchet de comentarios
5
Sin catálogos de archivosNo hay README por dominio ni listas de archivos o métodos: la estructura y los nombres se explican solos. Un README solo existe si el paquete tiene una API pública que mapear.como T3
6
Test junto al archivo, con el mismo nombrearchive.ts → archive.test.ts, también la integración. test/ guarda solo helpers y fixtures compartidos. T3 tiene 1.258 tests así y solo 15 aparte.check:structure
7
Sin código muertoknip pasa de solo reportar a bloquear.knip, error
8
Un PR deja todo más chico o igualSi solo mueve código, también tiene que borrar algo.regla de builders

Formato de tests

Unidad junto al código

describe("archiveSession", () => { it("archives an idle session", …) it("refuses while a turn runs", …) })

Un describe por unidad y un it por comportamiento, escrito como "hace X cuando Y".

Integración también junto al código

routes.test.ts arranca el engine real en un home temporal y habla HTTP. test/ guarda solo helpers y fixtures (makeSession(), homes temporales).

Prohibido

Leer el código fuente como texto · timers reales · el store real · fixtures a mano: se usan builders como makeSession() en test/fixtures.

Documentación el modelo de T3 Code: poca y con reglas de qué entra

README.md ~120 líneas

Qué es y por qué · instalar · enlace a docs · cómo contribuir y desarrollar. Nada más.

AGENTS.md ~150 líneas

Un solo archivo en la raíz (CLAUDE.md = @AGENTS.md) con:

  • el glosario (sesión, turno, rail, panel, host…);
  • dónde vive el código, en 6 líneas y el mapa de dominios;
  • criterio, cómo verificar, qué documentar y qué no commitear.

docs/ 3 carpetas

user/: cómo usar cada feature.
operations/: publicar, desarrollar, depurar.
internals/: decisiones y trampas que cruzan componentes.
Más un README índice.

Qué NO entra

Catálogos de archivos o métodos · narrar el flujo del código · resúmenes de PRs · planes, investigaciones y borradores (eso vive en el issue). "Los agentes pueden leer el código."

Workflows y scripts

Hoy

Un verify.yml de 61 KB corre todo en cada PR. Hay 9 workflows escritos sobre la marcha, 30 scripts planos, y source-invariants.mjs de 111 KB con reglas mezcladas.

Después

ci.yml detecta qué apps cambiaron y llama solo a sus workflows (ci-engine, ci-web…). Releases: uno por plataforma. Scripts: checks/ ci/ release/ dev/. source-invariants se parte en checks con nombre.

Cómo llegamos cada paso deja main en verde

1Acordareste blueprint + AGENTS.md con glosario y mapa
2Guardascheck:structure, fronteras y tamaño, en modo aviso
3Engineplatform/ + domains/, absorbiendo la descomposición de EngineStore
4Contratoengine-client por dominio
5Websrc/features + ui + platform; la descomposición del cockpit cae ahí
6Desktop + iOSsrc/ y Features/ con los mismos nombres
7Cerrardocs, CI por app, y las guardas pasan de aviso a error

Headless, sesiones como sub-agentes y el recorte de comentarios siguen, pero ya dentro de domains/ y features/: cada PR aterriza en su lugar definitivo.
