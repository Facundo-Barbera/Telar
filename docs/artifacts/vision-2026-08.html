Telar · Vision · August 2026

Docs are the interface.
Environments are the scarce resource.

Telar stops competing with the chat cockpit. Its job starts before the chat — deciding what work exists — and after it — verifying and accepting. In between, an environment scheduler makes N parallel agents survivable on one 24 GB machine.

01Four pillars

Interface
Documentation
Writing docs is how agents are programmed. Intent is the artifact being curated — never re-explained per session.
Workers
Looms
Self-verifying units of work in isolated worktrees. The shape for the 10% you don't babysit — not the front door.
Gate
Verifier
Observe-only, cannot edit code, cannot make itself pass. Load-bearing once pickup is unsupervised.
Scheduler
Env leases
Live stacks are pooled and leased, sized to review bandwidth (k≈1–2), not agent count.

03The environment scheduler

Build lanes

typecheck · unit tests · no Docker — N in parallel, nearly free
wt-auth-codes building
wt-kb-search building
wt-invite-flow unit ✓ → wants verify
wt-export-csv unit ✓ → wants verify

Verify pool  k = 1

full stack · browser · real RAM — a queue, not a fan-out
wt-billing-fix holds lease · repairing
wt-invite-flow queued #1
wt-export-csv queued #2
The reframe: you review one thing at a time, so the pool matches review bandwidth, not agent count. A lease is held through verify and repair, released on green. Cheap tiers (unit → integration → live) run in parallel; only the heavy tier queues. A loom can reach “ready pending live-verify” without touching Docker.

04The contract — five verbs, one cost class

# ~/.telar/projects/<id>/env.yaml — the sidecar
version: 1
env:
  cost: heavy        # none | light | heavy
  up: bun run up     # idempotent, slot-isolated
  ready: curl -sf :$TELAR_PORT_BASE/health
  reset: bun run db:reset
  down: bun run down
  tiers:
    unit: bun test            # cost: none
    live: bun run test:e2e   # leased heavy env

# Telar injects: TELAR_SLOT · TELAR_PORT_BASE
#                TELAR_WORKTREE · TELAR_LEASE_ID
costmeaningpolicy
noneLibrary. Tests need no services.Unlimited parallel.
lightA process or two, no containers.Per-worktree, cap 4.
heavyContainers, DBs, real RAM.Leased pool, k = 1.
verbsemantics
upIdempotent; never touches other slots.
readyExit 0 when usable; polled with timeout.
resetClean data state; else down + up.
downSafe on an already-down slot.
verifyOptional; else the Verifier drives directly.

05Rules that keep it honest

No adapters, ever

Telar never knows Docker or Supabase exist. The project's scripts absorb all weirdness. If onboarding a project requires changing Telar, the contract is wrong — bump to v2, never special-case.

Sovereignty

Telar config is personal, like editor config. Nothing Telar-shaped is committed to a shared repo. Adaptation lives in the sidecar; upstream only tool-neutral improvements a teammate who's never heard of Telar would thank you for.

Onboarding is an agent's job

telar init = an agent reads the repo, writes the mapping, and proves it — lease slot 1, ready, reset, down, ports in range. You accept it like any loom.

Isolation per database, not per container

One Postgres, N databases. Supabase/Neon branching where available — zero local RAM for per-worktree data.

06Sequencing

  1. Freeze the contract on paper — env-contract-v1.md. Done.
  2. Orchestrator speaks it by hand — its slot system is ~90% there; sidecar mapping only.
  3. Build the lease daemon — no UI — telar env lease / release / status. If this alone changes how many agents run in parallel, the thesis is confirmed.
  4. Onboarding agent vs. ozom-gv — the test of generality.
  5. Only then: docs-as-interface + triage loop — the surface comes last.
