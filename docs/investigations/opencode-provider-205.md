# OpenCode provider investigation — Telar #205

Investigation date: 2026-09-09. Recommendation for review; no implementation or runtime certification.

**Recommend an opt-in, local OpenCode driver using the official v2 JavaScript client over HTTP + SSE, with Telar owning one server process per Telar session and reusing it across turns.** Start with an existing OpenCode login, a qualified provider/model selection, supervised approvals, streaming, durable continuity, cancellation, and the existing browser/session MCP walls. Keep external OpenCode servers, multiple independent credential homes, shared chat servers, native subagents/background tasks, and advanced interaction controls for later stages. The plugin approval bridge must be verified before exposing #191 tools to this driver.

Current T3 Code really supports OpenCode: it registers `OpenCodeDriver` in the built-in driver array, constructs the adapter, and imports the official SDK. This is implementation evidence, not an inference from a README. ## Proposed driver and lifecycle

Use the SDK's client factory against a Telar-owned server. The SDK server convenience helper lacks an explicit binary path, cwd and environment patch in its public options, defaults to fixed port 4096, and injects `OPENCODE_CONFIG_CONTENT` itself. Those choices conflict with Telar provider-instance identity. Own `spawn(resolvedBinary, [serve, hostname, port])`, use `127.0.0.1` and an ephemeral port, bound startup output and timeout, and verify health/version before requests. Generate process-local server credentials and do not journal their values. [O packages/sdk/js/src/v2/server.ts:5-11](https://github.com/anomalyco/opencode/blob/830d5eb5354874105cc31599635a80c1662609e8/packages/sdk/js/src/v2/server.ts#L5-L11) [O packages/sdk/js/src/v2/server.ts:22-47](https://github.com/anomalyco/opencode/blob/830d5eb5354874105cc31599635a80c1662609e8/packages/sdk/js/src/v2/server.ts#L22-L47) [L apps/engine/src/cli-resolution.ts:39-40](https://github.com/Facundo-Barbera/Telar/blob/4d2c31448c2fddce06ffef94bade664a6c39428d/apps/engine/src/cli-resolution.ts#L39-L40)

Separate three lifetimes: (1) process runtime keyed by Telar session and provider-instance identity; (2) durable OpenCode session history; (3) active Telar claim owning observation and approval sinks. Reuse the process across normal turn boundaries. Rebuild only for identity/config/cwd changes, process death or deliberate eviction. Rebind active callbacks each turn and revoke stale leases. An idle provider must never execute against a completed Telar claim. Native background/autonomous work should be disabled or refused in milestone one; do not advertise `stopTask` or provider-initiated turns until their lifecycle is mapped.

A runtime identity should include resolved binary/version, provider instance, relevant environment patch (including explicit deletions), real cwd, relevant instruction/config identity, and non-secret MCP lease generation. It must not put bearer tokens in diagnostics. Model and variant are per-message inputs in OpenCode; do not automatically restart a server for every model change. However, changed account/config/host must never silently reuse the old identity. This is a design recommendation informed by #201, not permission to modify its fingerprint code.

Start the event stream and wait for connection before submitting a prompt. Allocate a client message ID, save it with the Telar turn mapping, and use `promptAsync`. Its HTTP completion is only admission: the handler forks work and returns no content while errors arrive separately. Settle a Telar turn only when its submitted message is accounted for and current session state agrees it is finished. [O packages/opencode/src/server/routes/instance/httpapi/handlers/session.ts:311-328](https://github.com/anomalyco/opencode/blob/830d5eb5354874105cc31599635a80c1662609e8/packages/opencode/src/server/routes/instance/httpapi/handlers/session.ts#L311-L328)

For resume, validate that the persisted ID belongs to the expected host, instance and directory. Differentiate confirmed missing history from 401, transport failure and 5xx. T3 explicitly distinguishes definitive not-found errors and forks on cwd movement; Telar should make history loss visible rather than quietly start over. [T apps/server/src/provider/Layers/OpenCodeAdapter.ts:93-101](https://github.com/pingdotgg/t3code/blob/6c583620ff7ad3235b135af7107c0543467eecfa/apps/server/src/provider/Layers/OpenCodeAdapter.ts#L93-L101) [T apps/server/src/provider/Layers/OpenCodeAdapter.ts:2885-2941](https://github.com/pingdotgg/t3code/blob/6c583620ff7ad3235b135af7107c0543467eecfa/apps/server/src/provider/Layers/OpenCodeAdapter.ts#L2885-L2941)

Telar already has the essential early durable cursor seam, including interrupted turns. Use it; do not add a second cursor store owned by the driver. [L packages/engine-client/src/protocol/observations.ts:120-132](https://github.com/Facundo-Barbera/Telar/blob/4d2c31448c2fddce06ffef94bade664a6c39428d/packages/engine-client/src/protocol/observations.ts#L120-L132) [L apps/engine/src/state.ts:8124-8136](https://github.com/Facundo-Barbera/Telar/blob/4d2c31448c2fddce06ffef94bade664a6c39428d/apps/engine/src/state.ts#L8124-L8136) Optional versioned metadata can later bind an ID to host/profile identity; adding an opaque JSON envelope inside the existing string requires considering the 512-character observation limit. A simple native session ID plus explicit stored binding is clearer for the first milestone.

On reconnect, subscribe first, buffer incoming frames, fetch current status/messages and pending requests, then merge by stable IDs. The SDK's retry loop does not make the upstream stream replayable. A timeout after sending a prompt can mean accepted work whose response was lost: inspect the client message ID before any retry. Do not blindly resubmit a mutation. If execution cannot be resolved, mark the outcome uncertain and stop automatic dispatch until reconciled. [O packages/sdk/js/src/v2/gen/core/serverSentEvents.gen.ts:91-111](https://github.com/anomalyco/opencode/blob/830d5eb5354874105cc31599635a80c1662609e8/packages/sdk/js/src/v2/gen/core/serverSentEvents.gen.ts#L91-L111) [O packages/sdk/js/src/v2/gen/core/serverSentEvents.gen.ts:222-230](https://github.com/anomalyco/opencode/blob/830d5eb5354874105cc31599635a80c1662609e8/packages/sdk/js/src/v2/gen/core/serverSentEvents.gen.ts#L222-L230)

Cancellation must serialize against prompt admission and future sends. Abort the provider session, recover pending request state and ensure descendants cannot keep executing after a claimed stop. T3 contains explicit descendant cleanup, which is useful regression evidence, not proof of all detached shell termination on every host. Keep a bounded fallback kill for an owned, unresponsive server; never kill an external server. Preserve history for a later turn. ## Approval guarantees and the plugin seam

The usable guarantee is specific: an OpenCode tool that reaches `Permission.ask` with an ask rule waits before its guarded action. Edit's diff is prepared before the ask and the write follows approval. MCP execution similarly follows the permission wait. [O packages/opencode/src/tool/edit.ts:101-111](https://github.com/anomalyco/opencode/blob/830d5eb5354874105cc31599635a80c1662609e8/packages/opencode/src/tool/edit.ts#L101-L111) [O packages/opencode/src/session/tools.ts:398-409](https://github.com/anomalyco/opencode/blob/830d5eb5354874105cc31599635a80c1662609e8/packages/opencode/src/session/tools.ts#L398-L409) This does not establish that every native extension uses that guard or that an approved shell has OS-enforced workspace isolation.

Proposed first policy: explicit supervised rules, no native autonomous/background delegation, ask for actions that need Telar's policy, route decisions through `onRequest`. Unknown permission names become reviewable `tool_call` requests or a typed refusal; never an implicit allow. Keep explicit upstream denies at least as restrictive unless the human's configured Telar mode intentionally overrides them. This precedence must be documented and fixture-tested rather than copying T3's rule list wholesale.

Send `once` upstream for individual Telar grants, including calls Telar auto-accepts through its own scoped policy. Implement persistent/session approval at Telar's existing gate; OpenCode's `always` cache outlives an individual native conversation in a shared directory instance. Do not map the two enums by name. On denial, reconcile other pending requests in that OpenCode session: the current reply implementation rejects them too. [O packages/opencode/src/permission/index.ts:121-139](https://github.com/anomalyco/opencode/blob/830d5eb5354874105cc31599635a80c1662609e8/packages/opencode/src/permission/index.ts#L121-L139)

Browser and sessions walls already contain their own scoping/policy mechanisms. Mount them as remote MCP with `Authorization: Bearer …` and `oauth: false`; use fixed Telar server names. Names OpenCode exposes for MCP tools must be translated through the existing common naming helpers, preserving the original provider call ID. Avoid a second approval for a wall that already gates its action, but do not blanket-allow every tool beginning with `telar`.

**The #191 distinction is material:** dirty `PluginToolSocket` does not gate execution, while its host owns tool classification. The OpenCode MCP ask has empty metadata and a tool reference; original arguments must be recovered from the correlated message/tool part (or a verified message read) before classifying. If the adapter cannot produce the actual call and host policy decision, fail closed. The socket must not receive the execution first and be treated as approved afterward. [O packages/opencode/src/session/tools.ts:81-88](https://github.com/anomalyco/opencode/blob/830d5eb5354874105cc31599635a80c1662609e8/packages/opencode/src/session/tools.ts#L81-L88) [O packages/opencode/src/session/tools.ts:407-409](https://github.com/anomalyco/opencode/blob/830d5eb5354874105cc31599635a80c1662609e8/packages/opencode/src/session/tools.ts#L407-L409)

Do not implement a competing plugin registry or reintroduce hardcoded DS/LaTeX into the new driver. Dirty #191 already defines one shared listener, per-session token, and non-secret generation for rebind identity. A generation changes even when URL does not. During a rebind, update or recreate OpenCode MCP registration before revoking the old lease; stale calls must fail and no new call may use old project authority. **D:** `plugins/socket.ts:51-68,126-144`; `worker.ts:708-716,831-834`; `driver.ts:1965,2098-2104`.

First milestone can proceed without waiting for #191 if it explicitly refuses sessions requiring unsupported plugin capabilities and exposes the limitation in preflight. Integration with #191 should be a focused followup after its contract is reviewed, or included only once the gate is fixture-proven. It must not silently omit required tools.

## Discovery, identity, usage and host boundaries

OpenCode is a harness containing many model providers. Persist `driver = opencode`, `instanceId = the configured OpenCode runtime`, `model = providerID/modelID`; split model slugs on the first slash only. Do not create a new Telar driver for every underlying service. Preserve custom provider IDs and long model IDs. Read the SDK's provider inventory through a worker-owned allowlisted metadata projection, filter/label connected versus merely catalogued providers, and preserve returned defaults. Connected status does not prove a live token or a paid request will succeed. No such request belongs in inventory refresh.

## Risks and acceptance plan

Highest risks are approval bypass through an ungated plugin MCP wall, same-directory cross-session MCP/remembered-grant leakage, duplicate execution after ambiguous prompt admission, stale idle events completing a new turn, and resume into the wrong auth/host identity. Other material risks are raw discovery payload credential exposure, config startup side effects, SDK/server version drift, misleading usage totals and incorrect remote filesystem assumptions.

Run deterministic tests with a fake `opencode serve` executable/HTTP+SSE server and temp-only state. Do not instantiate upstream runtime against a live home merely to get fixtures. Proposed acceptance cases:

- Binary missing/wrong version/invalid health, split startup line, port collision, timeout, early exit, abort during startup; no leaked process or MCP lease.
- One session/two turns reuses server and upstream ID; two Telar sessions in the same cwd get separate server scopes and tokens. Identity changes rotate runtime; environment deletion differs from omission; reordered equivalent config does not churn it.
- Cursor observed before first answer survives stop/crash; get 404 is handled visibly; 401/500/timeout never silently erase history. Cwd movement has a defined fork/refuse policy.
- Event subscription established before prompt; interleaved text/reasoning/tools, duplicates, snapshot after deltas, late frames and unknown event types produce one coherent timeline.
- Prompt accepted then HTTP response lost: recover by message ID, never send twice. Stale idle before/after admission cannot end a newly submitted or steered turn.
- Native command/edit/web/MCP requests do not execute before the gate; deny executes nothing; unknown permission does not allow. User questions stay parked in every runtime mode. Telar remembered grant never changes another session's permissions.
- Plugin gate uses the actual args and host classification; empty metadata cannot become a default approval. Rebind at same URL changes generation/token; disabled plugin disappears; revoked token and cross-project token fail. Confirm exactly one approval at the responsible gate.
- Disconnect at text/tool/approval/idle boundaries; recover pending requests and history without duplicated output or execution. Permanent loss is a typed failure/uncertain outcome, not apparent success.
- Pause blocks queued followups, provider wakeups and resume until human resume; stop races with admission/approval completion/child launch; owned hung server cleanup is bounded. Parent stop verifies no known child work remains.
- Usage fixture: two steps with cache + reasoning, cumulative message snapshots and duplicate step delivery, aborted partial turn, child work, compaction/model change, unknown price. Counts are not doubled; missing measurements stay missing.
- Discovery: two instance homes with different provider/model inventories, custom IDs containing additional slashes, disabled providers, variants absent/present, expiry without paid ping; same driver cache never contaminates another instance/directory/host; a fake secret in raw provider `key` never reaches metadata, logs or journal.
- Protocol roundtrip/persistence migration: old Claude/Codex data unchanged; new driver survives journal/restart; old worker/client is refused explicitly; no token/password enters journal or logged fingerprint.
- Packaging smoke using fake binary only on desktop and standalone worker; `/v2` import resolves after bundling. Real deployment matrix and paid/model acceptance run require separate authorization and budget.

Focused regression suites should cover driver selection, worker pause/steering/resume, provider instances/catalogs, protocol parsers, approvals and browser/session/plugin sockets; after #201 merges, keep its identity/usage/wait tests. No heavy gates were run for this report. No implementation has been accepted or shipped by completing the investigation.
