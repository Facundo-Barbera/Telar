# Telar Vision — August 2026 reflection

*Outcome of a reflective round on why Telar hasn't become the daily home it was
meant to be, and what it should become. This document is the "why"; the
normative companion is [`env-contract-v1.md`](env-contract-v1.md).*

## The diagnosis

Telar had a crisp thesis — *generation is solved, verification is the moat* —
and a full implementation of it (now frozen in `apps/web_old`), yet it never
became the tool reached for daily. Two findings explain that:

1. **The loom was the front door, and looms are too heavy for 90% of daily
   work.** Daily development is "rename this", "why is this failing". A loom
   (scope → orchestrate → build → verify → accept) is the right shape for the
   10% — shipping work you don't want to babysit — not for every interaction.
2. **The cockpit competed with the driving tool already in use (t3 code) and
   lost.** Mimicking a chat cockpit guarantees Telar is a worse copy of
   something that already exists.

## The product

**Documentation is the interface. Looms are the workers. Verification is the
gate. The environment scheduler is the scarce-resource manager.**

The daily loop:

- The human writes and curates **intent** — docs, specs, decisions. Writing
  docs is how the agents are programmed; project context is the artifact being
  curated, not something re-explained per session.
- Agents **pick up work from intent** and implement it in isolated worktrees.
  The pickup mechanism starts as a triage agent that reads doc diffs and
  *proposes* looms for one-click approval; fully autonomous pickup comes only
  after that stage earns trust.
- The **Verifier** (independent, observe-only) checks results against the
  contract. A green verify moves a loom to `ready`; the human always accepts.
  Unsupervised pickup makes the verifier load-bearing, not optional.
- **Live meddling is an escape hatch, not the core.** Perfecting a UI or
  debugging live means opening t3 code / a terminal *in the loom's worktree*.
  Telar does not rebuild the chat cockpit. Telar's job starts before the chat
  (deciding what work exists) and after it (verifying and accepting).

## The bottleneck: environments, not agents

Parallel agents are cheap; parallel *environments* are not. On a 24 GB
machine, "test every worktree's implementation" with a full Docker stack per
worktree is unaffordable — and it's also the wrong requirement.

The human reviews one thing at a time, so the environment pool only needs to
match **review bandwidth (k = 1–2 live stacks)**, not agent count (N
worktrees). Loom phases have wildly different costs:

- **Build** (writing code, typecheck, unit tests): no environment. N in
  parallel is nearly free.
- **Verify** (browser against a running stack): needs a live environment —
  but verification is a *queue*, not a fan-out.

This yields the **environment lease**: a pool of k environments; a loom
requests a lease when it reaches verify, holds it through repair, releases on
green. Cost levers on top:

- Isolation per **database**, not per container, where possible (one Postgres,
  N databases; Supabase/Neon branching for zero local RAM).
- **Verification tiers**: unit/typecheck (no env) → integration (light env) →
  live browser (heavy env). Cheap tiers run for all worktrees in parallel;
  only the heavy tier queues through the pool. A loom can reach "ready pending
  live-verify" without touching Docker.

## Generality without adapters

Telar never understands projects. It speaks a **dumb, fixed contract** — five
verbs and a cost class (see `env-contract-v1.md`) — and the project's own
scripts absorb all weirdness. Two rules keep this honest:

- **Onboarding is an agent's job, verified by the moat.** `telar init` = an
  agent reads the repo, writes the contract mapping, and *proves it* by
  leasing an environment end-to-end. The human accepts the onboarding like any
  loom.
- **If onboarding a new project requires changing Telar, the contract is
  wrong — fix the contract, never the project.**

## The sovereignty rule

**Telar config is personal, like editor config. Nothing Telar-shaped is ever
committed to a shared repo.**

- All per-project adaptation lives in a sidecar (`~/.telar/projects/<id>/`,
  keyed by remote URL): the contract mapping, any glue scripts.
- The verbs *name* what the repo already has (`up: bun run up`); only a
  genuinely missing verb gets a private sidecar script.
- When a piece of adaptation would help everyone, it is upstreamed as
  **tool-neutral repo tooling with zero Telar dependency** (precedent: the
  orchestrator slot system). Committability test: a teammate who has never
  heard of Telar reads the diff and says "nice, worktrees work better now."

## Sequencing

1. Freeze the five-verb contract on paper (`env-contract-v1.md`).
2. Make the orchestrator repo speak it by hand (it is ~90% there via its slot
   system) — through a sidecar mapping, not repo changes.
3. Build the standalone lease daemon (`telar env lease` / `release`) against
   it. No UI. If this alone changes how many parallel agents get run, the
   thesis is confirmed.
4. Send an onboarding agent at ozom-gv as the test of generality.
5. Only then: the docs-as-interface surface and the triage/pickup loop.
