**CLIProxyAPI audit: Claude compatibility, latency, streaming, and cache behavior**

Read-only investigation, September 8, 2026 in Mexico City / September 9 UTC. This is an addendum to the preserved [Telar/T3 report](../claude-audit/REPORT.md), not a replacement. No configuration, installed application, credentials, live sessions, or production source were modified. No provider requests, installations, restarts, or traffic rerouting were performed.

**Finding**

There is a concrete local compatibility mismatch: the configured Claude fingerprint is **2.1.258**, while a Claude executable **2.1.261** was observed connected to the proxy. CLIProxyAPI 7.2.145 requires exact version equality to recognize a native client. A normal 2.1.261 User-Agent therefore fails this check, even with all other native signals present. Under the default Claude OAuth policy, that selects request cloaking, which rewrites system placement, headers, cache markers, and session identity handling.

This is the strongest actionable finding. It is **not proof of repeated cache resets or the cause of the historical Fable delays**. The actual headers, credential route, retries, and transformed payloads from that run were not retained. A stable rewritten prefix can still cache very well, as the Fable usage observations suggest.

**What the Claude request actually passes through**

The Messages endpoint reads the request and selects streaming from its body. It goes through the auth manager and selected provider executor. A Claude-format request routed to the Claude executor does not automatically pass through the OpenAI or Codex translators. The registry's fallback preserves the body except a required model-name normalization: P [registry:65–104](https://github.com/router-for-me/CLIProxyAPI/blob/d9cea8904b14fbbebb77ef26e98ef08f6b48a724/sdk/translator/registry.go#L65). Aliases or a different provider route could select translation; historical route evidence is missing.

For a recognized native caller, incoming beta headers are preserved with credential-scoped OAuth additions. For an unrecognized OAuth caller, the proxy reconstructs its CLI beta profile and can drop caller extensions on the Anthropic origin. It includes thinking-redaction behavior when `thinking.display` is absent. This could contribute to empty visible reasoning, but does not measure the time spent reasoning. P [header policy:722–807](https://github.com/router-for-me/CLIProxyAPI/blob/d9cea8904b14fbbebb77ef26e98ef08f6b48a724/internal/runtime/executor/claude_executor_request.go#L722).

The request-rewriting feature is called `cloaking` in upstream source. Its default OAuth path replaces the top-level system with a minimal CLI identity and billing block, moves retained caller system blocks after the first user turn for supported/unknown modern models, and inserts a current-date reminder. Legacy models use user-message reminders. It does not simply discard every caller instruction in default non-strict mode. P [system transformation:211–243](https://github.com/router-for-me/CLIProxyAPI/blob/d9cea8904b14fbbebb77ef26e98ef08f6b48a724/internal/runtime/executor/claude_executor_cloaking.go#L211), [policy:945–1056](https://github.com/router-for-me/CLIProxyAPI/blob/d9cea8904b14fbbebb77ef26e98ef08f6b48a724/internal/runtime/executor/claude_executor_cloaking.go#L945). This can change model behavior and prefix structure even when subsequent calls reuse that structure successfully.

Unrecognized callers also lose the original Claude-specific session header and `metadata.user_id` as inputs to upstream UUID selection. Other protocol identifiers or a derived conversation identity are used, with a random UUID only as the final fallback. This is separate from the affinity selector, which reads original client signals. Thus the version mismatch does not establish that credential affinity also fails. P [identity:24–60](https://github.com/router-for-me/CLIProxyAPI/blob/d9cea8904b14fbbebb77ef26e98ef08f6b48a724/internal/runtime/executor/helps/claude_credential_identity.go#L24).

The pipeline also supports payload rules, thinking normalization, optional mid-system rebuilding, signature sanitation, MCP aliases, credential metadata, and final billing-signature normalization. The global config has no active payload section; credential-specific options remain unknown. MCP aliases are derived from the downstream caller and original tool names, not regenerated from each selected upstream credential. Existing valid MCP names are preserved. This is contrary evidence to assuming all MCP names rotate each call: P [request tool mapping:1155–1225](https://github.com/router-for-me/CLIProxyAPI/blob/d9cea8904b14fbbebb77ef26e98ef08f6b48a724/internal/runtime/executor/claude_executor_request.go#L1155).

**Cache behavior and what can invalidate it**

Anthropic documents exact prefix matching over tools, system, then messages. Prefix/model changes, expiration, or crossing supported organization/workspace cache boundaries can prevent reuse. Generation time consumes the cache lifetime; caching does not remove output-generation work. A changed ordinary HTTP request ID alone is not evidence of a changed prompt prefix. [Anthropic prompt caching, accessed September 9 UTC](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

The installed proxy's behavior is conditional:

- Recognized native clients retain their own cache placement. Independently, all requests still pass the four-breakpoint limiter and TTL-order normalizer.
- When the proxy owns placement, it ensures system/recent-message markers and uses a tools marker when there is no cacheable system. Its CLI fingerprint path upgrades markers lacking an explicit TTL to one hour; explicit TTLs survive. A one-hour block after an earlier five-minute block is downgraded by removing its TTL. See P `claude_executor_stream.go:124–155` and `claude_executor_cloaking.go:1093–1199,1259–1347`.
- The one-hour **session-affinity** retention is a local credential-binding TTL. It does not set the Anthropic prompt-cache TTL. In normal healthy reuse it refreshes the existing binding; failover, missing/changed session signals, expiration, or a proxy restart can reselect a credential. P [selector:704–786](https://github.com/router-for-me/CLIProxyAPI/blob/d9cea8904b14fbbebb77ef26e98ef08f6b48a724/sdk/cliproxy/auth/selector.go#L704).
- HTTP connection pooling and TLS resumption are separate again: P [transport:218–221,285–348,369–405](https://github.com/router-for-me/CLIProxyAPI/blob/d9cea8904b14fbbebb77ef26e98ef08f6b48a724/internal/runtime/executor/helps/utls_client.go#L285) reuses an Anthropic transport keyed by proxy URL. Creating an executor HTTP client per call does not imply a fresh TCP/TLS connection or prompt-cache reset.
- The proxy's thinking-replay cache is gated to compatible non-OAuth API-key routes, not the ordinary Claude OAuth path. It is not Anthropic prompt caching: P [replay eligibility:22–34](https://github.com/router-for-me/CLIProxyAPI/blob/d9cea8904b14fbbebb77ef26e98ef08f6b48a724/internal/runtime/executor/claude_thinking_replay.go#L22).

Stable cloaking can remain cacheable. A client version/config change that switches between native and cloaked paths is a concrete reason to expect a different prefix; per-call rewrites alone do not establish repeated misses. Billing/signature and undocumented identity internals need actual provider cache evidence, not assumptions about how every serialized byte is tokenized.

Current Claude Code docs distinguish main-conversation/Agent SDK TTL policy from subagents and helpers, and subscription usage from billed usage. They also require gateways to forward the beta header needed for one-hour caching. These controls must be assessed together with the proxy's rewrites. [Claude Code caching, accessed September 9 UTC](https://code.claude.com/docs/en/prompt-caching). No TTL changes are recommended solely from the observed quiet gaps.

**Latency and accounting: what is measured and what remains unknown**

The preserved Fable sample spans 41.75 minutes: 102 read/command envelopes total 3.958 seconds, while 19 journal gaps longer than 30 seconds total 36.46 minutes. Its longest gap is 255.715 seconds. These are engine observations, not a proxy timing breakdown. The supplied usage observation has `309592 / (309592 + 1868 + 32) = 99.390%` cache reuse on reported input. None of those measurements shows repeated misses.

Proxy retry rounds can revisit eligible credentials after 403/408/429/500/502/503/504 responses. A 90-second wait is allowed only when the cooldown fits that ceiling; a longer cooldown is not simply truncated to 90 and retried. Three allowed rounds can contribute up to 270 seconds of cooldown waiting under the global settings, plus actual attempt time; this is an illustrative bound for those waits, not the duration of every request. Credential failover within a round and SDK retries outside the proxy complicate attempt counting. Header-specific Claude rate-limit parsing adds bounded grace and treats a Fable-only rejection separately from shared account rejection: P [rate-limit parsing:14–67,113–145](https://github.com/router-for-me/CLIProxyAPI/blob/d9cea8904b14fbbebb77ef26e98ef08f6b48a724/internal/runtime/executor/helps/claude_ratelimit.go#L14).

The optional handler-level streaming bootstrap retry count defaults to zero here; auth-manager retries still apply. The HTTP response headers are withheld until a deliverable first chunk. The upstream client has no whole-request timeout in this call (`NewUtlsHTTPClient(...,0)`); the configured `X-Stainless-Timeout:600` is a header, not `http.Client.Timeout`. This permits long upstream waits without proving one occurred.

Once streaming starts, a blank SSE delimiter triggers forwarding and HTTP flush. The synthetic delimiter fixture shows how early upstream bytes can coexist with a late downstream event; it does not show that Anthropic omitted delimiters. Socket reads, decompression, event assembly, auth/handler channels, downstream writes, SDK consumption, and Telar persistence can each delay visibility. Proxy TTFT tracks the first response-body byte starting before RoundTrip, not the first visible reasoning/text token or end-to-end UI latency (`usage_helpers.go:139–189,363–395`). A ping or message-start event can make TTFT short while useful output remains late.

Anthropic's stream usage updates are cumulative within a message; nested start usage and later deltas must be merged by message identity rather than added. [Official streaming reference](https://platform.claude.com/docs/en/build-with-claude/streaming). The proxy's `sync.Once` avoids duplicate publication but can publish incomplete input/cache/output accounting. This affects its own ledger; native forwarding does not replace those usage fields. Telar's separate cumulative-query-cost issue remains as documented in the earlier report. Neither proxy ledger totals nor repeated Telar envelopes should be treated as exact billable totals without request/message IDs and final usage.

**Installed versus current upstream**

M changes the default software profile from 2.1.220 / SDK 0.94.0 to 2.1.258 / SDK 0.112.1, updates helper recognition, introduces additional continuity handling, and narrows one-hour TTL handling for subagents/probes. These changes are visible in [M device profile](https://github.com/router-for-me/CLIProxyAPI/blob/7fac6b15bcfe5ea55c18c9eaec8e5b7e6457d974/internal/runtime/executor/helps/claude_device_profile.go#L23) and [M stream path](https://github.com/router-for-me/CLIProxyAPI/blob/7fac6b15bcfe5ea55c18c9eaec8e5b7e6457d974/internal/runtime/executor/claude_executor_stream.go#L239).

Crucially, **M still uses exact version equality** at `claude_device_profile.go:215–217`. Merely upgrading to this pinned main would not demonstrate support for the observed 2.1.261 client. The local .258 User-Agent paired with .94.0 package version also spans different upstream baseline generations. That is compatibility drift, not proof of rejection. No update or header edit was attempted.

**Smallest practical plan**

1. Address native-client compatibility as a focused change. Validate the full .261 request shape, distinguish trusted client recognition from the proxy's outbound emulation baseline, and test classification across CLI patch upgrades. Do not simply spoof a newer User-Agent or disable all compatibility safeguards. Keep native system/tool/cache/session fields stable where supported.
2. Add bounded metadata-only observability before tuning retries: one downstream request ID, pseudonymous session and credential IDs, caller version/native-detection result, resolved provider/model, attempt number, status, cooldown duration, request byte counts, first-byte/first-SSE/first-useful-output/end timestamps, final usage, and cache marker/TTL summaries. Record hashes of relevant sections only when needed; no prompt, header dump, token, or raw tool-result capture. Current full request logging is broader than this requirement.
3. Expose proxy wait/attempt totals and SDK retry/rate-limit signals in Telar. Keep the current affinity policy unless measured rebindings justify a change. A bounded per-interaction retry budget can improve responsiveness, but reduce it only after quantifying whether retries recover requests or merely postpone an error.
4. Correct proxy usage aggregation independently: seed from `message_start.message.usage`, merge cumulative deltas, publish final totals once on completion (with an explicit partial/failure record on termination). Keep this separate from Telar cost accounting.

Suggested regression protocol for the authorized implementation phase: fake upstream only, 12 scripted requests covering matched/mismatched versions, unchanged versus changed session IDs, two credentials with affinity/failover, cache-marker preservation/TTL ordering, output-only versus full usage deltas, pre-stream 429/503 recovery, mid-stream failure, fragmented SSE, and slow-reader cancellation. Assert exact upstream attempt counts, preserved native prefix sections, final usage, and event-forwarding bounds. Use a virtual clock for 90-second cooldowns. Benchmark warmed 100 KB/1 MB/4 MB synthetic histories with stable tool lists, reporting allocations and p50/p95 translation/first-event delay separately. No heavy suite or installed-service tests ran in this audit.

No paid benchmark is needed to establish the compatibility mismatch. Any future live comparison requires a separately approved call/token/cost ceiling and fresh disposable sessions; this report authorizes none. Historical proxy latency attribution remains unknown until suitable metadata exists.
