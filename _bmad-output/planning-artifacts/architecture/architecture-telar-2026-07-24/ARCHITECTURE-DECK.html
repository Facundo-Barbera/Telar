Each spec is internally coherent. Nobody was wrong. Nobody owned the overlap — which is precisely the condition under which independently-built units diverge.

the diagnosis

Four shared surfaces, three owners each

Everything in the spine closes one of these, or closes a seam that closing them opened.

the paradigm

Three laws, one per layer

A single paradigm was rejected: the collisions are boundary-shaped, and any framing that makes boundaries a footnote gives a builder nothing at the moment they need it.

1 Control

Functional core, imperative shell. Core decisions pure over integers, sets and injected clocks. Non-determinism only in agent() leaves. Ratifies what project-context.md already says.

2 Boundaries

Ports & adapters. Every cross-module crossing is a typed port. MCP servers drive; MapStore, provider harness and service lane are driven. No module reaches into another's store.

3 State

Log + lazy projection — where declared. Holds for the ultra journal, drift ledger, evidence, usage ledger. Does not hold for workspace packets, lanes, manifests.

Why law 3 is scoped so explicitly

One spec says “the map is a regenerable projection.” A reasonable builder generalizes that and event-sources the workspace store — which holds the user's verbatim captured notes and must never be rebuilt from anything. The boundary between the two classes is an AD, not a judgement call at the call site.

state · AD-5 · AD-20

One owner per subtree — and the hole that left

The seam: AD-5 assigns owners to subtrees, so it never reached root-level state belonging to no module. Two modules could each append their own record shape to one shared file while both technically obeying it. AD-20 makes the owning core service the sole writer.

weak refs → tombstone, never throwtolerant readersversion only packet.yaml — it holds raw verbatim

sessions · AD-9 · AD-10 · AD-11

Config became data — without loosening the moat

The 103 KB chat route was already accreting session kinds (planner, steerer) as branches. Three more features meant three more branches.

Before

if (!project) … · if (isPlanner) … · if (isSteerer) …

Workspace's project-less master would be a fourth guard threaded through cwd, guardrails and settingSources.

After

A typed SessionProfile resolved before the route body. Project, master, loom-node and steerer are profiles. A new surface adds one — it does not add an if.

Making session config data is exactly the move that could turn a structural invariant into a configurable one. — why AD-10 exists
  • The PreToolUse guardrail is wired outside the profile and runs for every session regardless.
  • toolPolicy is intersect-only — typed to carry deny lists and allow-narrowing. No field can re-enable an accept path.
  • Separate routes per session kind were rejected on this ground alone: a moat enforced in three places has three chances to be forgotten.
  • AD-11: a profile declares required harness capabilities; an unmet one is a hard error before the stream opens. Codex silently receives no MCP today — a Codex master would answer “where did I stop” from nothing.
ui · AD-12 · AD-13

Freeze the contract, not the queue

Three features carve one 151 KB file. Hard serialization puts a big refactor on everyone's critical path; parallel carving guarantees the conflict and produces the seventh hand-built copy.

The contract is the artifact, not the code. The spine freezes the four slots and the registry; an epic-0 story does the carve-out; the three features build owner adapters against fixtures meanwhile. Only final wiring waits.

The seam: a registered renderer must be a pure function of (payload, shell view state) — otherwise ultra's anchor reads its own React context, loom's card reads its payload, and TranscriptView, which provides neither, can render nothing.

events · AD-14 · AD-21

Two delivery classes settle an apparent contradiction

UW CAP-1 agent-facing

“a run finishing produces an unprompted assistant turn summarizing the result”

OW CAP-1 human-facing

“the surface never initiates contact — it answers only when arrived at”

Not actually in conflict: one wakes an agent, the other refuses to interrupt a human. But nothing wrote that down, so the next builder reads one spec and gets it wrong in one direction or the other.

Every event carries a required delivery class. “Notifications are a dead channel for him” stops being a remembered habit and becomes something the type system asks about.

The seam AD-21 closes

With the event catalogue deferred to each module's epic, nothing stopped looms renaming loom:landed to loom:consolidated during unrelated work — silently breaking the workspace subscription that makes queue rows disappear. Published event names are a port contract, as binding as tool signatures. Deferring the catalogue is only safe because of this.

runtime · AD-17 — the collision nobody's spec saw

maxAgents: 12 is currently meaningless

A real defect no single spec could find — it only appears holding all three at once. A build fan-out fills every slot and verification queues behind it, which is the loom system's own diagnosed failure reproduced by the scheduler.

Verification gets precedence, not a held-open slot. A hard reservation was built and rejected: it broke the existing peak === 4 test, because holding a slot for an idle verifier burns 25% of a 4-slot machine to insure against a wait that's already bounded. No-barging plus priority wakeup gets the same protection free — a verify waits one in-flight call, and no slot idles with work queued.

Two corrections from reading the code: there is no interactive-session class — the chat route calls query() directly and never joined this gate at all. And the old gate could exceed its own ceiling: a woken waiter did active++ without re-checking, so an arrival racing a release over-committed the pool.

the mistake worth remembering

A rule against three counters nearly created a fourth

AD-18 was first written as a new root-level spend.ndjson — reasoning that ultra's manifest spend, loom charter budgets and the session usage display shouldn't be three counters that can disagree.

The repo already ships it

~/.telar/usage.ndjson — an append-only ledger written by logUsage() in apps/web/lib/store.ts, with UsageEntry carrying account, model, sessionId, costUsd, plus usageSummary() and a plan-usage.json projection.

It was asserted from the SPECs rather than checked against the code. AD-18 now extends the ledger that exists.

In a brownfield spine, every “we should have X” is a claim about the codebase — and the codebase is the only place it can be checked. — the reason that reviewer lens is configured

And it turned up one more thing

store.ts:8 hardcodes ~/.telar while manifest.ts, looms.ts, session-log.ts, permissions.ts and vcs.ts all honor TELAR_HOME. So chat history and usage do not isolate under ~/.telar-dev. Pre-existing, unrelated to any spec — and now the first unit of Track A, because building the spend ledger on it would write dev spend into production state.
