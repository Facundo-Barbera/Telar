Act I · First Principles Thinking

The Question Underneath the Question

The session opens ready to talk about verification-as-concept. It gets settled almost immediately — and immediately turns out not to be the real problem.

The Opening Snag

insight

Verification-as-concept settles fast: it's just observing reality against a pre-planned expectation. The session's real problem was never that. It's the how — actually setting up a verification system that works.

insight

The agents already know how to act — Playwright, shell commands, the easy part. What's hard is everything underneath them: databases, dev servers, background services with no one-fits-all shape.

insight

Telar's actual missing primitive isn't a verification technique at all — it's background processes. Claude Code and Codex both attach a process to a shell; telar has nothing like that, at session level or at loom level. No way to know "this belongs to this."

the redirect

"Go find out how this actually works, before we philosophize any further."

directionA research fan-out gets launched mid-technique: three parallel investigations, dispatched before First Principles Thinking is even allowed to continue.

the research fan-outThree Scouts, Sent Out

Scout 01
Prior Art

"9 tools, 1 shape."

  • 9 distinct readiness mechanisms in the wild: http, exec, tcp, grpc, notify-socket, watchdog, fixed-delay, log-regex, socket-activation. Kubernetes alone splits startup vs. readiness vs. liveness.
  • A convergent minimal declaration set: command, cwd, env, readiness signal, conditioned depends_on, stop signal + grace, restart policy, ownership token.
  • Ownership, defined precisely: declaration + one token → enumerate and tear down everything this run created, touching nothing from any other run.
  • "No one-fits-all" — partially refuted. The field set converges hard; only the readiness mechanism and the token vary, and both are enumerable.
Scout 02
Claude Code & Codex

"Two levels, one failure mode."

  • Claude Code has two lifecycle levels: in-session background commands (id, cursored output, stop-by-id) and whole-session background agents (a supervisor daemon) — it mirrors telar's own session/loom split exactly.
  • Codex has only one coarse tier: a unified-exec PTY. Kill-all only. No live stream.
  • Convergent failure across both: no ownership tagging → orphans reparented to PID 1, duplicate dev servers on port conflicts, a timeout that kills the wrapper but not its children, stale status.
  • Under Codex's sandbox, network is off by default in workspace-write — and the documented opt-out is silently broken on macOS. Port reachability can't be trusted without an explicit probe.
Scout 03
Telar's Own Codebase

"It was already here."

  • A near-complete lane/supervisor stack already exists — run-server.ts's startLane (ports, templated env, port injection, readyCheck, dependsOn) and supervisor.ts (restart-only-on-death, a crash-loop breaker) — reachable only from privileged verify/setup code, never from an agent's own tools.
  • The proactive "preparing" hook meant to run this (weave.ts's runSetup) is dead in production. Only a reactive, repair-time path ever fires.
  • The ownership shape telar needs already exists, once: a runner lease — ~/.telar/looms/<id>/.runner-lease — pid, token, timestamp, heartbeat, stale-reclaim.
  • Reframe candidate: this was never "design a process system." It's "unbundle the lane primitive already living inside telar."

The Big Idea

idea

Agents never spawn services themselves. They declare them through a tool — telar's own supervisor spawns, owns, leases, probes, and tears them down. Ownership by construction. Uniform across Claude Code and Codex. Orphans become structurally impossible.

idea

Model the tool surface on Claude Code's typed event shape — start / progress / notification, stop-by-id — not Codex's raw PTY polling.

landmark decision

"Agents declare. Telar spawns."

decisionAccepted — on two conditions. It has to feel as smooth as Claude Code's own background flow. And every process has to actually surface in the UI, for both sessions and looms.

One Running Server Per Line of Development

question

Loom process topology: global, or local? A loom is a branch; today, a worktree per thread. Spawn a service per worktree for verification — or unify on the branch?

idea

Leaning: a single server per loom branch, updated as each thread's worktree merges in. Worktrees stay optional-but-preferred for threads, mainly for collision avoidance. Accepted consequence — a thread working alone can't run server-dependent tests inside its own worktree. "Not bad."

the seed of everything that follows

"One running server per line of development."

insightHow Facundo already works, by hand, every day — an instinct from his own practice, offered almost in passing. It becomes the whole architecture by the time this session ends.

idea

Yes-and: that instinct becomes an evidence ladder —

rung 1

Worktree — cheap, serviceless evidence: tests, typecheck, lint.

rung 2

Landing on the loom branch — serial; each landing triggers a lane verify. Surface evidence, unambiguous blame: the thread that just landed owns any failure.

rung 3

Final ALL-verify — a cold, frozen lane. Evidence-grade.

idea

The loom's lane doubles as Facundo's window — a live URL onto the merged-so-far state. "Windows, not doorbells" — made physical. Want to see a thread's progress? Open the loom's URL. A "preview this thread" escape hatch stands an ephemeral lane on a thread's own worktree, human-triggered, torn down right after.

idea

Smoothness, defined precisely: an idempotent ensure_service(name) reuses a live lease instead of spawning a duplicate — killing the duplicate-dev-server bug (the same one that hit Claude Code as issue #9780) by design, not by discipline.

insight

Warm lanes raise a real cache-cleaning concern — and the database constraint is real: a full Supabase CLI stack is too heavy to run once per loom (RAM, weird dev behavior). One heavy stack, max. Never N.

idea

Service tiers enter the schema — scope: project | loom | ephemeral. Heavy infra (Supabase/Postgres) shared at project scope, refcounted; the app server warm per loom; ephemeral for previews and frozen finals. Isolation moves from the process layer to the data layer: a tenant-per-loom Postgres via TEMPLATE database — cheap, file-level copy. Supabase's gateway services (auth, PostgREST, storage) all point at one database, so isolation becomes declarable per service: tenant-db | schema | mutex | none. The warm-lane cache problem gets a declared answer instead of a vibe — hmr | restart | clean-restart, chosen by diffing against declared trigger paths. Final ALL-verify, recomposed: a cold app checkout + the shared warm infra + fresh tenant data cloned from template.

census

Most of the fleet is happy-path: one dev command, one port, no database. The outliers stress-test the schema — bixkuOS (three coordinated local processes, an env-derivation script, and a missing seed.sql), Focaltec (walled behind private CodeArtifact credentials), inboxdigest (a Gmail OAuth wall that simply can't be automated). New requirement class: "requires pre-provisioned X" — fail closed, not fail confused.

drift

Doc/code drift, confirmed in the wild: inboxdigest's README describes SQLite and a Claude CLI; the code runs remote Supabase and OpenRouter. Recipes must derive from code and env — never from a README. And a runtime-mismatch trap: texassite's vite dev never boots its serverless function; it needs vercel dev instead.

ports

Fleet-wide port collisions: four projects sit on stock Supabase ports (54321–9), three more on :8080. At most one such stack can run at a time — port planning has to happen at the fleet level, not just the loom level.

new classes

Install-phase gates (a GITHUB_TOKEN needed before anything builds), machine-global tool dependencies (a portless proxy daemon), generated migrations that must run before a reset, and mixed lockfiles that make package-manager detection ambiguous.

only proof

ozom-rent's 698-migration database reset validates the template-DB stamping approach — pay the reset once, copy it cheaply forever after. Only 2 of Ozom's 8 projects have a real test suite: for most of the fleet, surface verification isn't one option among several. It's the only verification there is.

the discovery
ozom-gv had already been solved

kickstart.ts — a script Facundo had already hand-written — turns out to already be a verification recipe, in shell form: idempotent, non-interactive, preflights docker and supabase, writes .env.local straight from supabase status, seeds the database, creates an owner account. bun run verify is already a full three-layer gate: unit tests, pgTAP, and a Playwright e2e suite with its own webServer.

The readiness node this whole session set out to design — Facundo had already built it, by hand, months before anyone asked.

The Worktree-Secrets Wall → a new field: carry

ozom-gv's supabase/.env.keys is gitignored, non-reconstructible, and missing from all twenty-plus of its existing worktrees — a fresh worktree can't even start Supabase. New schema field: carry — gitignored-but-required files that must be propagated into a lab's checkout. Absent from every piece of prior art surveyed. Telar-specific, and it surfaced only because someone actually looked at a real, lived-in project.

Orchestrator turned out to be the polyglot stress test — five services across three languages, a portless-proxy-plus-sudo wrapper baked into every dev script, a documented seed path that's actually broken, an existing telar.yaml gate that never runs its own 130-plus Python tests, and no /health endpoint on the main API at all.

Degraded modes have to be declared — "without secret X: data goes synthetic, feature Y turns off" — the contract narrows explicitly, instead of silently. And a project's own verify entrypoints (bun run verify, a Playwright suite) should be ingested as gates, with the lane owning the server underneath — never duplicated.

landmark decision · promise no. 2

"Only knock when it's truly dire."

decisionThe worst possible failure isn't a crash. It's a silent stall — gone for hours believing the project is advancing, while something broke and nothing moved.

The scarce resource was never spend. It's wall-clock time spent under false confidence. Silence has to be a guarantee — not merely an absence of noise.

Silent Stall Is the Enemy

— the dire razor

idea

Dire := the loom no longer has a viable path to advance without a human — stalled, parked, walled by a missing credential, crash-looping, or out of budget. That, and only that, gets pushed. Everything else — a failed test quietly entering repair, a flaky boot being retried — stays in the window. No knock.

idea

Two separate liveness layers: the supervisor already watches process liveness (restart-on-death, the crash-loop breaker). The orchestrator separately watches progress liveness — a heartbeat of actual advancement: evidence rungs climbed, landings made, verify rounds run. A flatline for N minutes is dire, even while every process shows green.

insight

A scope check: there's currently no way to solve anything from a phone — telar is a local, no-auth desktop cockpit. So pushes stay awareness-only: the knock kills false confidence, tells you it stopped and why, and resumes when you're back at your desk. Acting on it stays at the desktop.

Parked for later, not decided today — a companion website (not an app), Vercel-hosted, to authorize or answer things remotely. The caveat travels with it: that implies a relay, and remote accept is a harder, separate design problem from remote answer. Left deliberately for its own future pass.

The Stress Test

question

Three projects, each with a loom, plus a fourth loom on an extra dev path of one of them. Too many Supabase stacks? Should looms-per-project be limited? Does a session even attach? What happens when two looms' migrations collide?

The scenario exposes a hidden assumption — "a lab lives as long as its loom" — false. The evidence ladder had already made verification event-based (landings, finals); heavy infra can be leased just-in-time, per verify round, and released again.

idea

Just-in-time heavy leases, plus a fleet-level heavy-infra semaphore — one or two concurrent stacks by default, everything past that queues. Unifies neatly with the port serialization from cell B. The RAM fear dissolves through time-sharing, not through limits.

idea

Looms on the same project share that project's stack, refcounted. Migration divergence, handled two ways: plain-Postgres projects get tenant-db, each loom's branch migrations applied to its own tenant; gateway-mode projects (a real Supabase API) get mutex + reset-on-acquire, made cheap by a template cache keyed on the migration-set's hash.

idea

The trust wall: a session may adopt a stack the human already started, as a convenience. A loom never may. Evidence comes only from labs telar itself owns. "Adoption is allowed for working. Forbidden for proving."

Same Project, Two Looms

question

When two looms work the same project — same branch, or not? If not, how does verification even happen; if so, how is that even possible?

idea

Looms never share a branch — branch-per-loom is constitutional. Verification gets two proof layers instead: each loom proves its own branch, concurrently, in its own borrowed lab; the fleet's landing queue proves combinations serially — rebase onto the moved main, re-verify the same contract, merge.

idea

Ordering, resolved as accept-then-land: a human judges the branch's evidence; landing (rebase + re-verify) happens mechanically afterward. A failed landing re-verify reopens repair and only knocks if repair itself is exhausted. The alternative — land, then accept — would stall the whole queue on human latency.

idea

Stacked looms (the "extra dev path" case) become an explicit, declared relationship — loom B verifies against loom A plus its own delta, with a landing-order constraint. Never implicit.

One Working Directory

question

How can two branches even exist materialized on the same repo locally, without worktrees?

decision

Resolution: they can't. One working directory holds one checked-out branch, always. Concurrent same-project looms require separate materializations — which revises the worktree doctrine for good:

sacred

Facundo's primary checkout is for sessions only. Never looms.

mandatory

Worktree-per-loom — where the loom's branch actually lives, where the warm lane runs, where landings update, where carry files get planted.

optional

Worktree-per-thread stays preferred but not required; a single serial thread may just work directly in its loom's own worktree.

Two Altitudes, One Mutex

landmark decision

Two-altitude verification, locked.

Thread level — bmad-review-style: code review plus checks, serviceless, always runs.
Loom level — "is this what Facundo actually asked for?" A full lab standup; agents get a live Playwright playground; evidence comes out the other end.

Hard rule: only one loom verification per repo, at a time. A per-repo verification mutex.

insight

This is what finally unsticks the old bmad failure mode — threads that never reached approval — and makes full implementation testing possible at last. The loop finally closes.

idea

Consequence: window-on-demand for anything with heavy infra. Opening the window is the pull that borrows the stack — stand the lane up while you're looking, release it after. Infra-free projects just keep an always-warm window.

decision

What gets judged: the product the loom comes out with, after its own verify/repair loop converges on its own — the loom finds its own bugs and sends itself back to work. Final judgment lands on the ready product, "so I can see it in work." Landing itself is mechanical, after acceptance.

landmark decision

Rejection is a boomerang, not a bin.

decisionOn non-approval, Facundo can send the loom straight back with feedback to finish what it started. The loom keeps its branch, its worktree, its recipe. It resumes cheap.

A clean post-accept landing (rebase + contract pass) lands silently. If landing repair has to touch code, a delta note surfaces on the done card. A genuine contract failure reopens repair — and only knocks once repair itself is exhausted.

Act III · Devil's Advocate Courtroom

The Evidence on Trial

Not the architecture, this time. Its own witness. Five charges are brought against surface evidence — everything that could make it lie — and cross-examined one at a time.

01
The witness lies by omission.

A narrative claims a check passed but cites nothing to back it up.

new · this round

Evidence ledger. Harness-captured artifacts, and the narrative must cite them — uncited claims get marked unverified. "Excellent, hadn't thought of that."

02
The witness is unreliable under repetition.

A flaky pass looks identical to a solid one.

new · this round

Attempt history, kept on the card, plus a flaky flag. "Of course, we keep a history."

03
The witness doesn't know its own rank.

A cheap dev-grade run could pass for the release-grade proof that gates acceptance.

new · this round

Lab grades. Dev grade for landings, for speed; release grade for the accept-gating ALL-verify and the post-accept landing re-verify.

04
The witness was coached by a stranger.

Evidence could come from a stack the loom doesn't actually own — a borrowed environment, the wrong branch.

recalled · earlier this session

The trust wall and the per-repo verification mutex already forbid it — evidence comes only from telar-owned labs, one loom verification at a time.

05
The witness can go silent, and no one notices.

Absence of evidence could be mistaken for calm, rather than failure.

recalled · earlier this session

The dire razor and the progress-liveness heartbeat already answer this — a flatline for N minutes is dire, even while every process shows green.

All three new countermeasures approved outright; the other two charges, the court realized, had already been answered hours earlier.

Synthesis

The whole architecture is Facundo's own local workflow, formalized.

"One running server per line of development" became worktree-per-loom, a warm lane, and a per-repo verification mutex. The loom works the way its user already works.

Evidence, wearing three hats

Proof for the card, at acceptance. Proof-of-life for the heartbeat, at stall detection. Forensics for the courtroom, in the ledger and its provenance. Designed once, it serves all three.

The fleet pass paid the dividend

carry — the one genuinely novel field in the whole schema — and the kickstart.ts discovery both came from nowhere but looking at real, lived-in projects. Chosen direction: unbundle telar's existing lane stack; add leases, a tool surface, and wire the preparing hook back up.
