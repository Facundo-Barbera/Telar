The Warp & the Working Tree

Where should a loom's planning artifacts live — the decision graph, the PRD, the shared architecture doc — the repo, the home directory, or both? And when two looms reach for the same shared file, who wins? Adapt, don't rewrite, is the design value on the table.

01 · Trait Transfer

Graft patterns from systems that already solved this

Nine precedents pulled off the shelf — five about where things live, four about how writes are disciplined once they're shared.

Where things live

repo

bmad

_bmad-output lives in-repo, versioned with code — planning docs travel with branches and survive clones.

hybrid

Claude Code

Two-tier .claude/ (project, in-repo) + ~/.claude (global, home) — hybrid by artifact scope is an established pattern.

hybrid

npm

Manifest + lockfile (intent) in repo, cache (~/.npm) in home — declarations in repo, machine state in home.

home

Xcode DerivedData

Build/run artifacts NEVER in repo, always in ~/Library — run artifacts are disposable, knowledge is not.

hybrid

GitOps

Desired state lives in git, runtime status lives in the cluster — map = desired knowledge (git), loom runs = runtime status (TELAR_HOME).

How writes are disciplined

Event sourcing

Append-only event log + rebuilt projection — drift ledger = events, living map = projection; collisions become event merges, not file fights.

ADR practice

Architecture decisions as one-file-per-decision, append-mostly — new decisions add files instead of editing a monolith, shrinking collision surface to near zero.

Database WAL

Write-ahead log + checkpoint — looms write intent to a ledger first, map checkpoints lazily; crash-safe and collision-ordered by construction.

Git itself

Object DB (content-addressed, immutable) + working tree (mutable view) — store doc versions immutably, materialize the current view.

The pattern is unanimous across all nine: intent and knowledge go in-repo; runtime and machine state go in a home directory. Almost nobody puts run artifacts in the repo.

02 · Morphological Analysis

Cross the parameters: location × artifact-class × versioning × write-discipline

Before comparing options, one distinction collapses most of the debate.

Two artifact classes, two different physics. Loom-run artifacts (decision graph, flow DAGs, evidence, per-loom deltas) are single-owner and disposable-ish — no collision by construction. Project knowledge (the living map: PRD, architecture decisions, context, verification recipe) is shared and long-lived — collision-prone. The collision question only exists for class two.

A

All in-repo

.telar/ or docs/telar/

IN-REPOHOME

BenefitEverything versioned with code; branch-consistent map; reviewable in PRs; greppable by any agent with zero plumbing.

CostRepo pollution, planning-doc noise in commits; awkward on work repos you can't commit AI planning docs to; generated JSON/HTML artifacts are unmergeable.

B

All in TELAR_HOME

~/.telar/projects/<id>/

IN-REPOHOME

BenefitZero repo pollution; works on repos you can't commit to; single truth across worktrees; engine owns lifecycle with the existing atomic-write idiom; UI reads trivially.

CostMap not versioned with code (drifts from branch reality); invisible to in-repo tools; lost on a .telar wipe; doesn't travel with a clone to a new machine.

C

Hybrid, split by class

run → home · knowledge → repo

IN-REPOHOME

BenefitRun artifacts in TELAR_HOME (like today's manifest); living map + durable docs in-repo landing through the accept moat — maps 1:1 onto the existing design where run state is engine and knowledge is project.

CostNot separately logged — this is the one the contradiction resolves toward. See Synthesis.

D

Git-native sidecar

refs/telar/*

IN-REPOHOME

BenefitMap stored in the repo object DB (git-notes / gh-pages pattern) — versioned, travels if pushed, zero working-tree pollution, git merge machinery free.

CostExotic; invisible in a normal checkout; agents can't just read files; tooling and mental burden — the clever option that nobody can debug at 1am.

E

Sidecar repo

~/.telar/maps/<project>

IN-REPOHOME

BenefitMap gets its own git repo, optional remote — independent history, shareable across machines, clean separation.

CostTwo repos to keep correlated; map-version-to-code-version pinning becomes its own problem; the most machinery for the least gain at single-user scale.

Sub-option · gitignored in-repoFiles visible in the working tree for agents, never committed; gets pollution-free commits + file visibility but loses versioning and clone-portability — basically Option B wearing an in-repo costume.
Kept regardless · region granularityOne file per region (objective.md, architecture.md, surfaces.md, verification.md), not one monolith; fine-grained files shrink the textual collision surface massively.
Kept regardless · loom-run dir shape~/.telar/projects/<id>/looms/<loom-id>/{decision-graph.json, flow/*.json, evidence/} mirrors the existing filesystem-backed engine layout.

03 · TRIZ Contradiction

In-repo benefits and out-of-repo safety — no trade-off allowed

Every pure option loses something real.

IN-REPO

branch-consistency · reviewability · clone-portability

vs.

TELAR_HOME

work-repo safety · no pollution · cross-branch single truth

  1. 1

    MapStore adapter

    Engine reads/writes the map through one interface with two backends (in-repo dir | TELAR_HOME dir); location becomes a per-project setting, reversible later, one migration command between them.

  2. 2

    Per-project dial, smart default

    Personal repos default in-repo, work repos default home; the prep graph intake can even ask once at first loom and record the answer in project config.

  3. 3

    Regenerable map

    Treat the map as a materialized view of repo reality + decision ledger; if it's regenerable by a reconciliation loom, losing it is an inconvenience, not a catastrophe.

    Regenerability lowers the stakes of the whole location question — cache-like things can live anywhere; only unregenerable things (human decisions, accepted deltas) need durable, versioned homes.

  4. 4

    Split write-path from read-path

    Ledger entries (drift deltas, decisions) are the durable record and land in-repo via accept; the assembled map view is a derived file the engine can keep in TELAR_HOME and rebuild anytime.

  5. 5

    The fractal pattern already owns this

    Declare (delta) → validate (schema) → execute deterministically (serial land) → reconcile lazily (rebuild view); storage falls out of the pattern instead of being a new decision.

Wall #4 — nobody writes the map silently — already implies the collision answer. Looms never write shared docs directly mid-run; they emit proposals. Landing is serial through accept. File locking is unnecessary and wrong — looms run for hours, locks would starve the fleet.

04 · Failure Analysis

Pre-mortem: where this design dies

Collisions and loss scenarios, walked one at a time.

[FAIL]

Loom B lands a PRD adaptation that silently clobbers loom A's adaptation from an hour ago.

→ fix: every loom pins the map version (content hash) it read at prep. At land time, if head moved, run a mandatory rebase-adapt pass — a small agent job that re-applies the delta onto the new doc; the doc equivalent of rebase-and-reverify in the landing queue.

[FAIL]

Two looms make contradicting architectural decisions — a semantic collision, not a textual one.

→ fix: no storage layout fixes this; it's a judgment call. Surface both deltas side-by-side on the accept card and let the human rule — exactly what the accept moat exists for.

[FAIL]

A loom planned against a stale map — a staleness collision.

→ fix: the lazy intake diff already catches drift at prep; add the same diff at land time. Large drift triggers the existing bounded recompile event instead of blind landing.

[NOTE]

Three collision classes, three different owners — textual → fine-grained region files + rebase-adapt agent; semantic → human at accept; staleness → drift-diff at land + bounded re-plan. No locks anywhere.

[FAIL]

.telar gets wiped, or the work moves to a new laptop.

→ fix: run artifacts are acceptable losses (history), but accepted decisions must survive. Accepted deltas/decisions live in-repo (or its ledger); TELAR_HOME holds only regenerable views and run state.

[FAIL]

Generated JSON decision graphs land in the repo and produce unmergeable conflicts.

→ fix: rule — only human-meaningful markdown lands in-repo; machine artifacts (DAG JSON, evidence, HTML) stay in TELAR_HOME, referenced by loom id.

[FAIL]

Seven concurrent worktrees each carry a divergent in-repo map copy.

→ fix: fine, because landing is serial; but intake must always diff against the map at main/default-branch head, never against the worktree copy.

[FAIL]

A work repo gains a .telar/ dir and a coworker asks what it is.

→ fix: the per-project location dial defaults to home for repos with a non-personal remote; never commit planning docs without an explicit opt-in.

[FAIL]

The map dir in-repo gets hand-edited by the user directly, bypassing the ledger.

→ fix: that's allowed and good — human writes are never silent. The lazy intake diff absorbs it as drift, same as code drift.

[FAIL]

The PRD grows by accumulation as every loom appends its delta — the bmad epic-sediment problem returns.

→ fix: adapts-not-accumulates is enforced by making the LAND step an adaptation (rewrite-in-place of the region file), while the ledger keeps history. The doc stays lean because history lives elsewhere.

└── Synthesis

The question dissolves once split by class

Run artifacts (decision graph, flow DAGs, evidence) are single-owner engine state → TELAR_HOME under looms/<loom-id>/, collisions impossible by construction. Project knowledge (the living map: PRD, ADRs, context, verification recipe) is shared and durable → in-repo as fine-grained markdown region files by default, behind a MapStore adapter with a per-project repo|home dial (work repos default home). Collisions need no locks: pin the map hash at prep, propose deltas via the ledger, land serially at accept with a rebase-adapt pass; semantic contradictions go to the human on the accept card; staleness triggers drift-diff + bounded recompile. The ledger holds history so region files can adapt-in-place and stay lean — the anti-sediment move. The map is a regenerable projection, which lowers the stakes of location entirely.

accepted

Recommended direction

Option C — hybrid: run state in TELAR_HOME, knowledge in-repo — plus a MapStore per-project dial, plus a lockless ledger / serial-land collision protocol. Only human-meaningful markdown ever lands in-repo.
