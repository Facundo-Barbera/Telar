- (technique) started Morphological Analysis — parameters: location x artifact-class x versioning x write-discipline
- (insight by coach) there are TWO artifact classes with different physics: (1) loom-run artifacts (decision graph, flow DAGs, evidence, per-loom deltas) — single-owner, disposable-ish, no collision by construction; (2) project knowledge (living map: PRD, arch decisions, context, verification recipe) — shared, long-lived, collision-prone. The collision question only exists for class 2
- (idea by coach) Option A — ALL IN-REPO (.telar/ or docs/telar/ dir): everything versioned with code; branch-consistent map; reviewable in PRs; greppable by any agent with zero plumbing
- (idea by coach) Option A cost: repo pollution, planning-doc noise in commits, awkward on work repos where you cannot commit AI planning docs, generated JSON/HTML artifacts are unmergeable
- (idea by coach) Option B — ALL IN TELAR_HOME (~/.telar/projects/<id>/): zero repo pollution; works on repos you cannot commit to; single truth across worktrees; engine owns lifecycle with existing atomic-write idiom; UI reads trivially
- (idea by coach) Option B cost: map not versioned with code (drifts from branch reality); invisible to in-repo tools; lost on .telar wipe; does not travel with a clone to a new machine
- (idea by coach) Option C — HYBRID SPLIT BY CLASS: run artifacts in TELAR_HOME (like today's manifest), living map + durable docs in-repo landing through the accept moat — maps 1:1 onto the existing design where run state is engine and knowledge is project
- (idea by coach) Option D — GIT-NATIVE SIDECAR: map stored under refs/telar/* in the repo object DB (git-notes / gh-pages pattern) — versioned, travels if pushed, zero working-tree pollution, git merge machinery free
- (idea by coach) Option D cost: exotic; invisible in a normal checkout; agents cannot just read files; tooling and mental burden — the clever option that nobody can debug at 1am
- (idea by coach) Option E — SIDECAR REPO: map gets its own git repo (~/.telar/maps/<project> with optional remote) — independent history, shareable across machines, clean separation
- (idea by coach) Option E cost: two repos to keep correlated; map-version-to-code-version pinning becomes its own problem; the most machinery for the least gain at single-user scale
- (idea by coach) sub-option: in-repo but gitignored — files visible in working tree for agents, never committed; gets pollution-free commits + file visibility but loses versioning and clone-portability (basically Option B wearing an in-repo costume)
- (idea by coach) parameter worth keeping regardless of option: map region granularity — one file per region (objective.md, architecture.md, surfaces.md, verification.md) not one monolith; fine-grained files shrink textual collision surface massively
- (idea by coach) parameter: loom-run dir shape — ~/.telar/projects/<id>/looms/<loom-id>/{decision-graph.json, flow/*.json, evidence/} mirrors the existing filesystem-backed engine layout
- (technique) started TRIZ Contradiction — in-repo benefits AND out-of-repo safety, no trade-off
- (idea by coach) contradiction stated: in-repo gives branch-consistency, reviewability, clone-portability; home gives work-repo safety, no pollution, cross-branch single truth. Every pure option loses something real
- (idea by coach) resolution 1 — MapStore adapter: engine reads/writes the map through one interface with two backends (in-repo dir | TELAR_HOME dir); location becomes a per-project setting, reversible later, one migration command between them
- (idea by coach) resolution 2 — per-project dial with smart default: personal repos default in-repo, work repos default home; the prep graph intake can even ask once at first loom and record the answer in project config
- (idea by coach) resolution 3 — regenerable map: treat the map as a materialized view of repo reality + decision ledger; if it is regenerable by a reconciliation loom, losing it is an inconvenience not a catastrophe — and then WHERE it lives stops being a high-stakes decision
- (insight by coach) regenerability lowers the stakes of the whole location question: cache-like things can live anywhere; only unregenerable things (human decisions, accepted deltas) need durable, versioned homes
- (idea by coach) resolution 4 — split write-path from read-path: ledger entries (drift deltas, decisions) are the durable record and land in-repo via accept; the assembled map view is a derived file the engine can keep in TELAR_HOME and rebuild anytime
- (idea by coach) resolution 5 — the fractal pattern already owns this: declare (delta) -> validate (schema) -> execute deterministically (serial land) -> reconcile lazily (rebuild view); storage falls out of the pattern instead of being a new decision
- (insight by coach) wall #4 (nobody writes the map silently) already implies the collision answer: looms never write shared docs directly mid-run — they emit proposals; landing is serial through accept; therefore file locking is unnecessary and wrong (looms run for hours, locks would starve the fleet)
- (technique) started Failure Analysis — pre-mortem collisions and loss scenarios
- (idea by coach) failure: loom B lands a PRD adaptation that silently clobbers loom A's adaptation from an hour ago -> fix: every loom pins the map version (content hash) it read at prep; at land time, if head moved, run a mandatory rebase-adapt pass (small agent job: re-apply this delta onto the new doc) — the doc equivalent of rebase-and-reverify in the landing queue
- (idea by coach) failure: two looms make CONTRADICTING architectural decisions (semantic collision, not textual) -> no storage layout fixes this; it is a judgment call -> surface both deltas side-by-side on the accept card and let the human rule — exactly what the accept moat exists for
- (idea by coach) failure: loom planned against a stale map (staleness collision) -> the lazy intake diff already catches drift at prep; add the same diff at land time; large drift triggers the existing bounded recompile event instead of blind landing
- (insight by coach) three collision classes, three different owners: textual -> fine-grained region files + rebase-adapt agent; semantic -> human at accept; staleness -> drift-diff at land + bounded re-plan. No locks anywhere
- (idea by coach) failure: .telar wiped or new laptop -> run artifacts are acceptable losses (history), but accepted decisions must survive -> accepted deltas/decisions live in-repo (or its ledger), TELAR_HOME holds only regenerable views and run state
- (idea by coach) failure: generated JSON decision graphs land in repo and produce unmergeable conflicts -> rule: only human-meaningful markdown lands in-repo; machine artifacts (DAG JSON, evidence, HTML) stay in TELAR_HOME, referenced by loom id
- (idea by coach) failure: 7 concurrent worktrees each carry a divergent in-repo map copy -> fine, because landing is serial; but intake must always diff against the map at main/default-branch head, never against the worktree copy
- (idea by coach) failure: work repo gains a .telar/ dir and a coworker asks what it is -> per-project location dial defaults to home for repos with a non-personal remote; never commit planning docs without an explicit opt-in
- (idea by coach) failure: map dir in repo gets hand-edited by the user directly (bypassing the ledger) -> that is allowed and GOOD (human writes are never silent); the lazy intake diff absorbs it as drift, same as code drift
- (idea by coach) failure: PRD grows by accumulation as every loom appends its delta (the bmad epic-sediment problem returns) -> adapts-not-accumulates is enforced by making the LAND step an adaptation (rewrite-in-place of the region file), while the ledger keeps history; the doc stays lean because history lives elsewhere
- (insight) SYNTHESIS: the question dissolves once artifacts are split by class. Run artifacts (decision graph, flow DAGs, evidence) are single-owner engine state -> TELAR_HOME under looms/<loom-id>/, collisions impossible by construction. Project knowledge (living map: PRD, ADRs, context, verification recipe) is shared and durable -> in-repo as fine-grained markdown region files by default, behind a MapStore adapter with a per-project repo|home dial (work repos default home). Collisions need no locks: pin map hash at prep, propose deltas via ledger, land serially at accept with a rebase-adapt pass; semantic contradictions go to the human on the accept card; staleness triggers drift-diff + bounded recompile. Ledger holds history so region files can adapt-in-place and stay lean (anti-sediment). Map is a regenerable projection, which lowers the stakes of location entirely.
- (decision) recommended direction: Option C hybrid (run state home, knowledge in-repo) + MapStore per-project dial + lockless ledger/serial-land collision protocol; only human-meaningful markdown ever lands in-repo
