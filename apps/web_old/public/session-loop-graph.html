The Telar session loop

How a conversation actually runs — what we fixed, what's still fragile, and the shape to converge on. · Aug 8, 2026 · PR #86

Today — five doors, four waiting rooms, one gate

Everything funnels into one turn at a time, but each door has its own path there. The red boxes are the fragile parts: machinery the client runs, so it only works while a tab is open — and the engine has no timer of its own.

The bug ledger

FIXED Repeating "Compacted" divider

Reconnecting replayed the whole open window with no resume cursor, and the divider fold can't tell a redelivered event from a new one. Replay now serves from the cursor-addressed feed. events/route.ts

FIXED The "ultra stopped" marker loop

A stopped run's heal re-minted its timestamp on every read, so the wake could never be marked delivered — the tab re-woke the agent forever. The heal is idempotent now. ultra/storage.ts

FIXED Work lost when the process died

A CLI crash mid-window dropped everything you'd watched arrive — never saved, never closed. The last unflushed teardown path now flushes. session-runtime.ts

FIXED Codex re-told every wake, forever

An ack gate written before Codex received the prompt appendix was never updated when it started to. Delivery is now judged per run, per prompt — never per provider. route.ts

OPEN · D5 Stranded queue items

The engine only drains when kicked — turn end, queue traffic, boot. A message queued with no open tab can wait indefinitely. Needs a heartbeat.

OPEN · D8 Tab-dependent machinery

Wake polling, watch subscriptions and their injection queue live in the session view. No tab, no wake — and every remount resets their memory (today's loop rode exactly this).

OPEN · D6 Two send contracts

Main chat sends direct and queues on conflict; the dock always queues. Same session, different ordering and retry behavior when they race.

The shape to converge on

One durable mailbox, one always-on dispatcher. Your messages and machinery become tickets in the same line — each keyed to its event, so a wake can exist at most once per outcome and loops become structurally impossible. Tabs render; they never drive.

Your call — updated with the evidence

1 · Machinery goes server-side.

Ultra outcomes and watch firings enqueue mailbox tickets on the server, keyed per outcome. Kills D8. Both references do this — t3code structurally, OpenCode as its shipped subagent-completion fix. Strongly recommended.

2 · Fully synchronous — decided, heartbeat reversed.

Owner's call (Aug 8): every kick is an event, never a clock — t3code's posture. The engine subscribes to ultra:run-completed on the wake channel (the fast path) and runs one full machinery sweep at boot (the durable projections' guarantee, actualized after a restart). Accepted residuals, stated: a publish lost mid-process-lifetime, or a loom reaching a watch state (no bus event exists for looms today), strands until the next natural kick — turn end, queue traffic, boot. Follow-up recorded: declare an agent-facing loom state event in core to close the watch half.

3 · One send contract.

Every surface enqueues with a client-minted idempotency key; the dispatcher claims instantly when idle. Kills D6. t3code's command-receipt pattern validates it — one path, retries return the original result.

4 · Steering — priority raised.

t3code doesn't queue at all: a mid-turn message is fed into the running turn, same turn id, at the provider adapter. OpenCode wants this and hasn't shipped it. Telar's runtime already holds the streaming input channel, so after F2 this is closer than assumed — worth pulling forward rather than treating as a someday.

5 · Show the machinery.

A wake turn currently renders nothing until words arrive. As a mailbox ticket it can honestly show "waking for ultra sweep…" in the strip.
